# D-123 Git Flow 브랜치 전략을 쓰고, 운영 배포는 main에서만 한다

- 날짜: 2026-10-13
- 관련 항목: D-106(GitHub Actions 배포), D-108(릴리스 노트)
- 상태: 일부 변경됨 → D-124(태그는 자동)

## 결정
1. 브랜치를 Git Flow로 나눈다: `main`(운영), `develop`(다음 버전 작업 모음), `feature/<이름>`, `release/vX.YY`, `hotfix/vX.YY.Z`. 순서는 `CONTRIBUTING.md`에 적는다.
2. 배포 워크플로(deploy.yml)와 릴리스 노트 워크플로(release-note.yml)는 `main`에 push될 때만 돈다. 지금까지 쓰던 `deploy-docker` 브랜치는 은퇴한다.
3. 배포는 `release/vX.YY`(또는 `hotfix/*`)를 `main`에 합치고 `vX.YY` 태그를 다는 일이다. 릴리스 노트는 배포를 확인한 뒤 같은 release 브랜치에 더해 `main`에 한 번 더 합친다(노트만 바뀐 push는 배포하지 않음, D-108).
4. 처음 `main`에 합칠 때는 지금 운영 중인 v1.10과 같은 코드라 `[skip ci]`로 올려 다시 배포하거나 예전 릴리스 노트를 공지로 다시 올리지 않는다.

## 이유
과제 항목 "Git Flow 브랜치 전략 적용"(2026-10-13 사용자 요청). 사용자가 결정 카드에서 "운영 배포는 main만"을 골랐다.

## 이전 내용 → 바꾼 이유
- 작업은 `release/v1.05` 하나에 쌓고 `deploy-docker`로 배포, `main`은 첫 커밋만 있었음 → Git Flow로 나누고 `main`으로 배포(사용자 요청).
