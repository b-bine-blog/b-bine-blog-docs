# D-130 문서와 소스 코드를 저장소 두 개로 나눈다

- 날짜: 2026-10-14
- 관련 항목: D-123(Git Flow), D-128(CI)
- 상태: 확정

## 결정
1. 문서는 새 저장소 [b-bine-blog-docs](https://github.com/b-bine-blog/b-bine-blog-docs)에 둔다: `docs/`(요구사항·정책·결정 기록·설계·계획·장애 기록), `specs/`(기능별 명세·계획·데이터 모델·작업 목록), `.specify/`(개발 원칙), `.claude/skills/`(Spec Kit 명령).
2. 소스 저장소 [b-bine-blog](https://github.com/b-bine-blog/b-bine-blog)에는 코드와, 코드·테스트가 직접 읽는 파일만 둔다.
   - 테이블 정의: `docs/04-design/schema.sql` → `db/schema.sql` (테스트가 이 파일로 DB를 만든다)
   - API 계약: `specs/<기능>/contracts/*.yaml` → `api-contracts/*.yaml` (테스트가 실제 응답과 비교한다). 명세 쪽 `contracts/README.md`는 옮긴 위치를 가리킨다.
   - 개발환경: `docs/04-design/development-environment.md` → `DEVELOPMENT.md`
   - 그대로 남김: `README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `release-notes/`(배포 워크플로가 사이트 공지로 올린다), `deploy/`, `local/`
3. 결정을 새로 하거나 바꾸면 문서 저장소의 `docs/03-decisions/`에 남긴다. 두 저장소의 `CLAUDE.md`가 서로의 위치를 알려 준다.
4. 문서 저장소는 배포와 상관없다. 문서만 바꿀 때 소스 저장소의 테스트·배포가 돌지 않는다.
5. 2026-10-14 이전 명세·작업 목록에 적힌 옛 경로(`docs/04-design/schema.sql` 등)는 기록이므로 고치지 않고, 문서 저장소 README에 옮긴 위치를 적는다.

## 이유
GitHub 저장소에서 문서와 소스 코드를 나누라는 요청을 받았다(2026-10-14 사용자). 같은 저장소 안에서 폴더만 나누는 방법과 저장소를 따로 만드는 방법 중 사용자가 문서 저장소를 따로 만드는 쪽을 골랐다.

## 이전 내용 → 바꾼 이유
- 처음부터 소스 저장소 하나에 `docs/`, `specs/`, `.specify/`를 함께 두었다 → 문서와 소스를 나누라는 요청에 따라 문서 저장소를 따로 만듦(사용자 결정).
