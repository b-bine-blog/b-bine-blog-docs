# D-140 요청 제한 장부를 서버 메모리에서 DB 테이블로 옮긴다

- 날짜: 2026-10-19
- 관련 항목: SCL-01, SEC-03, 4.3(이중화 대비), D-129 #6, 001 R-08
- 상태: 확정

## 결정
1. IP·회원별 요청 제한(로그인 시도, 좋아요, 댓글 같은 트래픽 제한)은 DB 테이블 `rate_limits`에서 센다.
2. 앱 두 개(8370·8371, D-129)가 같은 장부를 보므로 한도를 함께 센다.
3. 세는 방식은 지금과 같은 고정 창이다. 창의 첫 요청 시각부터 정한 시간 동안 한도까지 받는다.
4. 키 원문(IP, 회원 번호)은 저장하지 않는다. 기능 이름과 합친 키의 SHA-256만 저장한다.
5. 부른 쪽이 예외로 되돌려져도 센 횟수가 남도록 새 트랜잭션에서 센다.
6. 장부를 쓰지 못하면(DB 오류) 요청을 막지 않고 통과시킨다. 로그인은 `login_failures` 잠금(SEC-03)이 따로 지킨다.
7. 창이 끝난 행은 04:00 정리 작업이 지운다.

| 컬럼 | 내용 |
|---|---|
| key_hash | 키의 SHA-256(유니크) |
| window_start | 창 시작 시각 |
| request_count | 창 안의 요청 수 |
| expires_at | 창이 끝나는 시각(정리 기준, 인덱스) |

#### 운영 DB에 실행할 문장
```sql
CREATE TABLE rate_limits (...);  -- 소스 저장소 db/schema.sql과 같음
CREATE INDEX idx_rate_limits_expires_at ON rate_limits (expires_at ASC);
```

주의: 한도 숫자와 창 길이는 지금 설정값 그대로다(D-68).

## 이유
앱을 두 개 띄우면서 각 앱이 따로 세어 실제 한도가 두 배가 됐다. Redis를 따로 두지 않고 이미 쓰는 MySQL로 함께 센다(2026-10-19 사용자).

## 이전 내용 → 바꾼 이유
- D-129 #6, SCL-01: 요청 제한만 1차에 서버 메모리(`InMemoryRateLimiter`)에서 세고 이중화 때 Redis로 옮긴다 → 지금 DB 테이블로 옮긴다. 이중화 때 Redis로 바꿀지는 4.3을 정할 때 다시 본다.
