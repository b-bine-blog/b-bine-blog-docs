# D-143 검색 "전체"는 후보 글 번호부터 모은다

- 날짜: 2026-10-21
- 관련 항목: 4.2, D-48, D-142, BRD-09
- 상태: 확정

## 결정
1. 검색 "전체"의 글 목록은 후보 글 번호부터 모은다.
   1. 제목은 FULLTEXT 인덱스로, 태그는 태그 이름으로, 작성자는 닉네임으로 각각 글 번호를 찾는다.
   2. 세 갈래를 합쳐 글마다 맞은 조건 수(hit)를 센다.
   3. 그 번호의 글만 공개 여부·차단을 확인하고 정렬한다.
2. 관련도순은 맞은 조건 수가 많은 순, 같으면 최신순이다. 이전과 순서가 같다.
3. 최신순·인기순도 같은 후보에서 정렬만 바꾼다.
4. 제목·태그·닉네임만 고르는 검색과 블로그 안 검색은 그대로 둔다.

## 이유
D-142 뒤에도 검색 "전체"가 글 30만 건에서 약 10초 걸려 성능 목표(D-48, 늦어도 2초)를 넘었다.

| 화면 | 전 | 후 |
|---|---|---|
| 전체 검색(관련도) | 10.0초 | 1.9초 |
| 전체 검색(최신순) | — | 1.9초 |
| 전체 검색(인기순) | — | 1.9초 |

#### 느렸던 원인
1. 제목·태그·닉네임 조건을 OR로 이었다.
2. OR로 이으면 MySQL이 제목 FULLTEXT 인덱스를 쓰지 못한다.
3. 그래서 글 30만 건을 모두 훑으며 글마다 세 조건을 따졌다. 개수 세기와 번호 찾기에서 두 번 훑었다.

#### 잰 방법
D-142와 같다. 검색어는 "여행"과 "게임"이다. 두 검색어 모두 첫 쪽 10건과 전체 개수가 이전과 같았다.

주의: 숫자는 작업 환경 MySQL(버퍼 풀 128MB)에서 잰 비교용 값이다. `p.id IN (... UNION ...)`으로 쓰면 MySQL이 글마다 하위 쿼리를 다시 돌려 빨라지지 않았다.

## 이전 내용 → 바꾼 이유
- 세 조건을 OR로 이은 한 쿼리 → 인덱스를 쓰도록 갈래마다 번호를 찾아 합쳤다.
