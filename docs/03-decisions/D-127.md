# D-127 운영 배포를 다시 도커 컨테이너로

- 날짜: 2026-10-13
- 관련 항목: D-105, D-106, D-126(무중단 배포), SCL-02, D-75
- 상태: 확정

## 결정
1. GitHub Actions가 jar(`bootJar`)를 만들어 저장소 루트 `Dockerfile`과 함께 서버 `~/blogproject`로 보내고, 서버의 `deploy/deploy.sh`가 `docker build`로 이미지(`mainttblog-app:<시각>`)를 만든 뒤 컨테이너로 실행한다. 이미지 파일을 통째로 보내지 않아 전송이 jar만큼만 든다.
2. 이미지에는 Java 21 실행 환경(`eclipse-temurin:21-jre`)이 들어 있어 서버에 깔린 Java 버전과 상관없이 돈다.
3. 컨테이너 이름은 `mainttblog-<포트>`. 무중단 배포(D-126)대로 8370과 8371을 번갈아 쓴다. `--network host`로 서버 포트를 바로 써서 nginx 설정과 DB 주소는 jar 때와 같다.
4. 비밀 값은 `docker run -e`로 넘기지 않는다. 같이 쓰는 서버에서는 다른 사용자가 `docker inspect`로 볼 수 있기 때문이다. 대신 나만 읽을 수 있는 `~/blogproject/secrets.env`(권한 600)를 만들어 컨테이너의 `/app/.env`로 붙이고, 앱은 원래 있던 `spring.config.import: optional:file:.env[.properties]`로 읽는다.
5. 컨테이너는 내 계정 uid로 돌아 업로드 파일(`~/blogproject/uploads` → `/app/uploads`, D-75)이 내 소유로 남는다. `--restart unless-stopped`로 서버가 다시 켜지면 같이 뜬다. 로그는 `docker logs mainttblog-<포트>`(20MB×3개까지).
6. 같은 서버의 다른 팀 컨테이너와 이미지는 건드리지 않는다. 지우는 것은 우리 이름(`mainttblog-*`)의 컨테이너와 지금 쓰지 않는 `mainttblog-app` 이미지뿐이다. 첫 도커 배포 때 예전 jar 방식 앱(PID 파일)을 멈춘다.

## 이유
jar 방식은 실행하는 컴퓨터에 맞는 Java(21 이상)가 있어야 뜬다. 사용자가 이 호환성 문제를 걱정해 도커 방식으로 바꾸기로 했다(2026-10-13). 같은 날 사용자가 "무료 한도 안에서는 도커를 써도 된다"고 D-106의 "도커는 사용하지 마"를 풀었고, 서버에서 우리 계정이 sudo 없이 도커를 쓸 수 있음을 확인했다(Docker 29.7.2).

## 이전 내용 → 바꾼 이유
- D-106: 도커 없이 `java -jar`로 실행 → 도커 컨테이너로 실행(사용자 결정, 서버 Java 버전과 무관하게).
- D-105와 다른 점: 이미지를 GitHub Actions에서 만들어 통째로 보내지 않고, jar만 보내 서버에서 이미지를 만든다(지난번 첫 시도가 이미지 만들기에서 오래 걸려 취소됨). 비밀 값은 파일로 붙인다.
