# D-129 배포 방식을 블루-그린에서 롤링으로 바꾼다

- 날짜: 2026-10-14
- 관련 항목: D-126(블루-그린), D-127(도커 컨테이너), SCL-01, 4.3(이중화 대비)
- 상태: 일부 변경됨 → D-140(6번 요청 제한)

## 결정
1. 운영 서버에 앱을 늘 두 개 띄운다: `mainttblog-8370`(`APP_PORT`)과 `mainttblog-8371`(`APP_PORT_B`). 둘 다 같은 이미지, 같은 DB, 같은 업로드 폴더, 같은 비밀 값 파일을 쓴다.
2. 배포(`deploy/deploy.sh`)는 8371을 먼저 새 버전으로 바꾸고 `/api/public-config`가 응답하면 8370을 바꾼다(롤링). 하나를 바꾸는 동안 다른 하나가 요청을 받는다. 옛 앱은 처리 중인 요청을 끝내고 내려간다(graceful, D-126에서 넣은 설정 그대로).
3. 8371의 새 버전이 뜨지 않으면 거기서 멈추고 8370의 옛 버전은 그대로 둔다. 8370만 실패하면 8371(새 버전)이 혼자 받는다.
4. nginx는 두 포트를 하나의 upstream으로 두고, 꺼지거나 응답이 없는 쪽은 건너뛴다(`deploy/nginx/mainttblog.java21.net.conf`, D-126과 같은 설정). 서버 nginx 설정은 2026-10-14 13:20에 적용했다(서버 파일의 Certbot https 줄은 그대로 두고 upstream과 proxy_pass만 고침). 같은 날 8370을 끈 채로 요청 5번이 모두 200인 것을 확인했다.
5. D-126의 `active-port`, `blue-green-on` 파일은 쓰지 않는다. 릴리스 노트 워크플로는 `APP_PORT`(8370)로 앱에 붙는다.
6. ~~앱마다 따로 세는 값(로그인 시도 횟수 같은 요청 제한, `InMemoryRateLimiter`)은 두 앱이 각자 센다. 공유 방법은 4.3 이중화를 정할 때 함께 정한다.~~ → D-140: DB 테이블에서 함께 센다. 예약 작업은 ShedLock이 한 앱에서만 돌게 한다.

## 이유
블루-그린은 평소 앱이 하나라 배포할 때만 안 끊기고, 평소에 그 앱이 죽으면 다시 뜰 때까지 사이트가 멈춘다. 롤링은 늘 두 개가 떠 있어 배포할 때와 평소에 하나가 죽었을 때 모두 다른 하나가 받으므로 안 끊길 가능성이 높다(2026-10-14 사용자 결정). 같은 날 사용자가 서버에서 앱 두 개(8370, 8371)를 동시에 띄워 둘 다 정상 응답하는 것을 확인했다.

한계: 두 앱이 같은 서버 한 대에 있어 서버가 꺼지면 둘 다 멈춘다. 서버를 나누는 것은 4.3 이중화에서 정한다.
