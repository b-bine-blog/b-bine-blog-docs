# D-142 글 목록은 글 번호부터 찾고, 그 번호의 글만 자세히 읽는다

- 날짜: 2026-10-21
- 관련 항목: 4.2, D-48, D-73, BRD-09, FR-058
- 상태: 확정

## 결정
1. 글 목록(메인 피드·검색·태그·공지·블로그 글 목록)은 두 번에 나눠 읽는다.
   1. 조건과 정렬로 한 페이지의 글 번호만 찾는다.
   2. 그 번호의 글만 본문·작성자·댓글 수를 읽고, 찾은 순서대로 돌려준다.
2. 번호와 전체 개수를 찾을 때는 글(posts)과 블로그(blogs)만 잇는다. 작성자 닉네임 검색은 하위 쿼리로 본다.
3. 번호를 찾을 때 MySQL에 "글 먼저, 블로그 나중" 순서를 알려 준다. 태그·구독 같은 하위 쿼리 순서는 MySQL에 맡긴다.
4. posts에 인덱스 2개를 더한다.

| 인덱스 | 쓰는 곳 |
|---|---|
| (status, board_type, created_at DESC, blog_id) | 최신순 목록, 메인 공지 |
| (status, board_type, like_count DESC, created_at DESC, blog_id) | 인기순 목록 |

#### 운영 DB에 실행할 문장
```
CREATE INDEX idx_posts_status_board_type_created_at_blog_id ON posts (status ASC, board_type ASC, created_at DESC, blog_id ASC);
CREATE INDEX idx_posts_status_board_type_like_count_created_at_blog_id ON posts (status ASC, board_type ASC, like_count DESC, created_at DESC, blog_id ASC);
```

주의: 인덱스는 저장소 `db/schema.sql`에 먼저 더했다. Crowfoot 문서 654에는 아직 반영하지 않았다.

## 이유
글 30만 건으로 재 보니 메인이 성능 목표(D-48, 늦어도 2초)를 크게 넘었다.

| 화면 | 전 | 후 |
|---|---|---|
| 메인 최신 글 | 17.8초 | 1.0초 |
| 메인 인기 글 | 13.9초 | 1.0초 |
| 메인 최신 글 1000쪽 | 26.8초 | 1.0초 |
| 제목 검색(흔한 단어) | 3.1초 | 1.9초 |
| 전체 검색 | 28.1초 | 10.0초 |
| 태그 검색 | 0.02초 | 0.01초 |

#### 느렸던 원인
1. MySQL이 블로그부터 읽고 글 30만 건을 본문째 정렬한 뒤 10건을 골랐다.
2. 인덱스에 게시판 종류가 없어 공지 3건을 찾으려고 글 전체를 읽었다.

#### 잰 방법
1. 작업 환경의 MySQL 8.0(버퍼 풀 128MB)에 `db/schema.sql`로 테이블을 만든다.
2. 글 30만 건, 회원 3,000명, 블로그 1,000개, 글 태그 60만 건, 댓글 30만 개를 넣는다.
3. 실제 앱을 띄워 화면마다 한 번 데운 뒤 5번 재고 중앙값을 적는다.

주의: 운영 서버의 메모리·데이터 양과 다르므로 숫자는 비교용이다. 전체 검색과 페이지마다 세는 전체 개수(약 0.6초)는 남은 과제다.

## 이전 내용 → 바꾼 이유
- 한 쿼리로 본문까지 읽고 정렬했다 → 데이터가 많을 때 본문째 정렬하는 일을 없애려고 번호부터 찾게 했다.
- D-73(피드는 볼 때마다 모아오기)은 그대로 둔다. 성능 목표 안으로 들어와 피드 테이블은 만들지 않는다.
