# 배포 방식: 도커 컨테이너와 예전 jar 직접 실행

운영 서버(https://mainttblog.java21.net)에 앱을 올리는 방식을 정리합니다.
지금은 도커 컨테이너(D-127)이고, 그 전에는 jar를 서버에서 바로 실행했습니다(D-106).

## 도커란

#### 한 줄 설명
앱과 앱이 돌아가는 데 필요한 것(Java 같은 실행 환경)을 **이미지**라는 상자 하나에 담고, 그 상자를 어느 컴퓨터에서나 똑같이 실행하는 도구입니다.

#### 용어
| 용어 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| Dockerfile | 이미지를 만드는 순서를 적은 파일 | 저장소 루트 `Dockerfile` |
| 이미지 | 앱 + 실행 환경을 담은 상자(읽기 전용) | `mainttblog-app:<배포 시각>` |
| 컨테이너 | 이미지를 실제로 실행한 것 | `mainttblog-8370`, `mainttblog-8371` |
| 볼륨(붙이기) | 컨테이너가 지워져도 남아야 하는 폴더를 서버 폴더에 연결 | `~/blogproject/uploads` → `/app/uploads` |

#### 우리 Dockerfile
```dockerfile
FROM eclipse-temurin:21-jre
ENV TZ=Asia/Seoul \
    FILE_STORAGE_ROOT=/app/uploads
WORKDIR /app
COPY app.jar app.jar
ENTRYPOINT ["java", "-Xmx512m", "-jar", "/app/app.jar"]
```

1. `FROM`: Java 21 실행 환경이 들어 있는 기본 이미지에서 시작합니다.
2. `ENV`: 시간대와 업로드 폴더를 정합니다.
3. `COPY`: 빌드한 jar를 넣습니다.
4. `ENTRYPOINT`: 컨테이너가 켜지면 `java -jar`로 앱을 띄웁니다.

## 지금 방식: 도커 컨테이너 (D-127, D-129)

#### 배포 순서
1. `main`에 push하면 GitHub Actions가 jar를 만듭니다(`bootJar`).
2. jar, `Dockerfile`, `deploy/deploy.sh`를 SSH로 서버 `~/blogproject`에 보냅니다.
3. 서버의 `deploy.sh`가 `docker build`로 이미지를 만듭니다.
4. 컨테이너 2개(8370·8371)를 하나씩 새 이미지로 바꿉니다(롤링, D-129).
5. 새 컨테이너가 `/api/public-config`에 응답하면 다음 것을 바꿉니다. 안 뜨면 멈추고 옛 버전을 그대로 둡니다.

#### 실행 옵션
| 옵션 | 하는 일 |
|---|---|
| `--network host` | 서버 포트를 바로 써서 nginx·DB 주소가 jar 때와 같음 |
| `--user $(id -u):$(id -g)` | 내 계정으로 실행해 업로드 파일이 내 소유로 남음 |
| `--restart unless-stopped` | 앱이 죽거나 서버가 다시 켜지면 자동으로 다시 뜸 |
| `-v ~/blogproject/secrets.env:/app/.env:ro` | 비밀 값을 파일로 붙임(다른 사용자가 `docker inspect`로 못 보게) |
| `--log-opt max-size=20m --log-opt max-file=3` | 로그를 20MB×3개까지만 남김 |

주의: 같은 서버를 다른 팀도 쓰므로 우리 이름(`mainttblog-*`)의 컨테이너와 이미지만 지웁니다.

## 예전 방식: jar 직접 실행 (D-106, 2026-10-12 ~ 10-13)

#### 배포 순서
1. GitHub Actions가 jar를 만듭니다.
2. jar와 `deploy.sh`를 SSH로 서버에 보냅니다.
3. `deploy.sh`가 PID 파일에 적힌 옛 앱 프로세스를 멈춥니다.
4. 서버에 깔린 Java로 새 앱을 띄웁니다.

```bash
setsid nohup java -Xmx512m -jar app.jar > app.log 2>&1 < /dev/null &
echo $! > app.pid
```

#### 특징
- 서버에 맞는 Java(21 이상)가 깔려 있어야 뜹니다.
- 비밀 값은 GitHub Actions가 SSH로 넘긴 값을 `deploy.sh`가 환경변수로 export해 앱에 넘깁니다.
- 로그는 `~/blogproject/app.log` 한 파일에 계속 쌓입니다.
- 앱이 죽으면 다음 배포 때까지 꺼진 채로 있습니다.

## 비교

#### 장단점
| 항목 | 도커 컨테이너 (지금) | jar 직접 실행 (예전) |
|---|---|---|
| 실행 환경 | 이미지에 Java 21이 들어 있어 서버 Java와 상관없음 | 서버에 맞는 Java가 있어야 함. 버전이 다르면 안 뜸 |
| 다른 컴퓨터로 옮기기 | 도커만 있으면 똑같이 뜸 | 컴퓨터마다 Java 설치·버전을 맞춰야 함 |
| 배포 속도 | 이미지 만드는 시간만큼 느림(기본 이미지는 한 번 받으면 재사용) | 가장 빠름(jar만 바꿔 실행) |
| 앱이 죽었을 때 | `--restart`로 자동으로 다시 뜸 | 사람이 다시 띄우기 전까지 꺼져 있음 |
| 서버 재시작 | 컨테이너가 같이 뜸 | 직접 다시 띄워야 함 |
| 여러 개 띄우기 | 이름·포트만 바꿔 같은 이미지로 여러 개(8370·8371 롤링) | 포트·PID 파일·로그를 따로 관리해야 함 |
| 되돌리기 | 옛 이미지가 남아 있으면 그 이미지로 다시 실행 | 옛 jar를 따로 보관해야 함 |
| 로그 | `docker logs`, 크기 제한 자동 | 파일 하나에 계속 쌓여 직접 정리 |
| 비밀 값 | 권한 600 파일을 읽기 전용으로 붙임 | 실행할 때 환경변수로 넘김 |
| 서버 자원 | 이미지 저장 공간이 더 듦(옛 이미지는 배포 때 지움) | 거의 안 듦 |
| 배우는 부담 | Dockerfile·이미지·컨테이너 개념을 알아야 함 | `java -jar`만 알면 됨 |
| 쓸 수 있는 조건 | 서버에서 도커를 쓸 수 있어야 함(우리 계정은 sudo 없이 가능) | Java만 있으면 됨 |

#### 정리
- **도커**는 "어디서나 똑같이, 죽어도 다시 뜨게"가 강점이고, 배포가 조금 느리고 개념을 배워야 하는 게 약점입니다.
- **jar 직접 실행**은 단순하고 빠른 게 강점이고, 서버 Java 버전에 묶이고 죽으면 꺼진 채로 남는 게 약점입니다.
