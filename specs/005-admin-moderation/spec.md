## 사용자 시나리오와 테스트 (User Scenarios & Testing) *(필수)*

우선순위는 요구사항분석서 3.5의 우선순위(ADM-01·02 상, ADM-03·04·06·07 중, ADM-05 하)를 따른다. 관리자 계정 분리(SEC-09)는 다른 모든 관리자 기능의 전제라서 사용자 스토리 1에 함께 넣었다.

### 사용자 스토리 1 - 관리자 전용 접근과 회원 조회 (우선순위: P1)

메인 관리자는 일반 회원과 분리된 관리자 계정(회원과 같은 users 테이블에서 role = ADMIN으로 구분, D-90)으로 관리자 페이지에 들어가 전체 회원을 검색하고 상세 정보를 본다. 이메일·전화번호는 기본으로 가려져 있고, "전체 보기"를 눌러야 원래 값이 보이며, 누른 기록이 남는다. 관리자가 아닌 사람은 관리자 페이지와 관리자 기능을 쓸 수 없다.

**이 우선순위인 이유**: 회원 관리(ADM-01)는 우선순위 상이고, 관리자 계정 분리(SEC-09)와 서버 쪽 마스킹(4.4, D-22)이 없으면 다른 관리자 기능을 안전하게 열 수 없다.

**독립 테스트**: 관리자 계정 하나와 일반 회원 계정 몇 개를 만들어 두고, 관리자 계정으로 회원을 검색해 상세 정보와 "전체 보기"를 확인하고, 일반 회원·블로그장·비회원으로 같은 관리자 기능을 요청해 거부되는지 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 메인 관리자 계정으로 로그인했을 때, **When** 관리자 페이지에서 회원을 검색하면, **Then** 일치하는 회원 목록이 보이고 회원을 누르면 상세 정보가 보인다.
2. **Given** 이메일 `abcdef@gmail.com`, 전화번호 `01012345678`인 회원이 있을 때, **When** 메인 관리자가 그 회원의 상세 정보를 처음 열면, **Then** 이메일은 `ab***@gmail.com`, 전화번호는 `010-****-5678`로 보이고 이름·닉네임은 보이며, 서버 응답에도 원래 이메일·전화번호가 들어 있지 않다.
3. **Given** 이메일 `ab@x.com`인 회원이 있을 때, **When** 메인 관리자가 상세 정보를 열면, **Then** 이메일은 `a***@x.com`으로 보인다(@ 앞이 2글자 이하면 첫 글자만).
4. **Given** 2번 화면에서, **When** 메인 관리자가 "전체 보기"를 누르면, **Then** 원래 이메일과 전화번호가 보이고, 누른 관리자·누른 시각·대상 회원이 관리자 활동 기록에 남는다.
5. **Given** 어느 화면에서도, **When** 메인 관리자가 회원 정보를 보면, **Then** 비밀번호 칸은 없다.
6. **Given** 일반 회원, 블로그장, 비회원이, **When** 관리자 페이지나 관리자 기능(회원 검색, 블로그 숨김, 경고 등)을 요청하면, **Then** 모두 거부되고 회원 정보는 응답에 들어가지 않는다.
7. **Given** 관리자 권한이 회수된 계정이 로그인 상태를 유지하고 있을 때, **When** 다음 관리자 기능을 요청하면, **Then** 거부된다.
8. **Given** 메인 관리자 계정으로 로그인했을 때, **When** 블로그 생성, 참여 신청, 블로그에 글쓰기, 댓글, 좋아요, 팔로우를 요청하면, **Then** 모두 거부된다. **And** 메인 공지(BRD-10) 작성과 관리 기능은 쓸 수 있다(D-90).

### 사용자 스토리 2 - 블로그 조회·숨김·강제 폐쇄 (우선순위: P1)

메인 관리자는 전체 블로그를 검색해 블로그장, 멤버 수, 글 수를 보고, 문제가 있는 블로그를 숨기거나 강제로 폐쇄한다. 강제 폐쇄도 블로그장 폐쇄처럼 누른 날짜 + 7일 04:00에 폐쇄되고(D-94), 관리자 폐쇄의 철회는 메인 관리자만 할 수 있다(블로그장은 철회할 수 없음, D-104).

**이 우선순위인 이유**: 블로그 관리(ADM-02)는 우선순위 상이고, 메인 관리자가 블로그 단위로 쓸 수 있는 가장 강한 조치다(3.7 폐쇄).

**독립 테스트**: 공개·일부 공개·비공개 블로그를 만들어 두고 관리자 계정으로 검색해 블로그장·멤버 수·글 수를 확인한 뒤, 한 블로그를 숨기고 다른 블로그를 강제 폐쇄해 목록·검색·접근 결과와 활동 기록을 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 멤버 4명(블로그장 포함)과 글 12개가 있는 블로그 A가 있을 때, **When** 메인 관리자가 블로그를 검색해 A를 찾으면, **Then** A의 블로그장, 멤버 수 4, 글 수 12가 보인다.
2. **Given** 공개 블로그 A가 있을 때, **When** 메인 관리자가 A를 숨기면, **Then** A는 메인 블로그 목록·검색·피드에 나오지 않고, 숨긴 관리자·시각·대상이 활동 기록에 남는다. A의 블로그장과 멤버는 평소처럼 A에 들어가 글을 쓰고, 멤버가 아닌 사람(비회원·구독자 포함)은 주소나 공유 링크로도 들어갈 수 없으며, A의 블로그장은 "운영" 탭의 끌 수 없는 알림을 받는다(D-103 #7).
3. **Given** 블로그 B가 있을 때, **When** 메인 관리자가 10월 2일 오후 3시에 B를 강제 폐쇄하면, **Then** B는 10월 9일 04:00 폐쇄로 예약되고, 블로그장을 제외한 멤버 전원과 구독자에게 10월 2일(즉시), 10월 6일 04:00(3일 전), 10월 8일 04:00(1일 전)에 폐쇄 예정 알림이 가며, 폐쇄한 관리자·시각·대상이 활동 기록에 남는다(D-94).
4. **Given** 블로그 B가 폐쇄된 날이 10월 9일일 때, **Then** B의 글·사진·카테고리는 그날부터 보이지 않고 11월 8일(30일 뒤) 처리에서 완전히 삭제되며, B의 주소는 30일이 지난 뒤에야 다른 블로그가 쓸 수 있다.
5. **Given** 블로그장이 아닌 일반 회원이나 다른 블로그의 블로그장이, **When** 블로그 B의 숨김·강제 폐쇄를 요청하면, **Then** 거부된다.
6. **Given** 3번의 B가 폐쇄 예정 중일 때, **When** B의 블로그장이 폐쇄 철회를 누르면 **Then** 거부되고(403 `ADMIN_CLOSE_LOCKED`) B는 폐쇄 예정 그대로이며, **When** 메인 관리자가 강제 폐쇄를 철회하면 **Then** B는 운영 중으로 돌아가고 블로그장을 제외한 멤버·구독자에게 철회 알림이 가며 철회한 관리자·시각·대상이 활동 기록에 남는다. 블로그장이 직접 폐쇄한 블로그는 관리자가 철회할 수 없다(409 `NOT_ADMIN_CLOSE`) (D-104).

### 사용자 스토리 3 - 블로그장 경고와 강퇴(권한 박탈) (우선순위: P2)

메인 관리자는 블로그장에게 경고를 준다. 경고는 블로그별로 세고 1년이 지난 경고는 빼며(D-95), 그 블로그에서 경고가 3번 쌓이거나 관리자가 바로 강퇴하면 그 블로그의 블로그장 권한을 박탈한다. 부블로그장이 있으면 가장 먼저 부블로그장이 된 사람이 블로그장이 되고, 없으면 블로그는 7일 유예 후 새벽 4시에 폐쇄된다. 박탈당한 사람은 그 블로그의 일반 멤버로 남는다.

**이 우선순위인 이유**: ADM-07은 우선순위 중이지만, 메인 관리자가 블로그 안 질서에 개입하는 유일한 사람 단위 수단이다(D-44). 블로그 조회(사용자 스토리 2)가 먼저 있어야 대상 블로그를 찾을 수 있다.

**독립 테스트**: 부블로그장이 있는 블로그와 없는 블로그를 하나씩 만들어 두고, 각 블로그장에게 경고 3번 또는 바로 강퇴를 적용한 뒤 역할 변경, 폐쇄 예정 시각, 알림, 활동 기록을 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 블로그 A의 블로그장 O가 경고를 받은 적이 없을 때, **When** 메인 관리자가 O에게 경고를 주면, **Then** O의 경고 수는 1이 되고, O는 "운영" 탭의 "블로그장 경고" 알림을 받으며 이 알림은 끌 수 없다.
2. **Given** O가 경고 2번을 받은 상태일 때, **When** 메인 관리자가 세 번째 경고를 주면, **Then** O의 블로그장 권한이 박탈되고 O는 "권한 박탈" 알림을 받는다.
3. **Given** O가 경고를 받은 적이 없을 때, **When** 메인 관리자가 바로 강퇴하면, **Then** 경고 수와 관계없이 O의 블로그장 권한이 박탈된다.
4. **Given** 블로그 A에 부블로그장 S1(10월 1일 지정)과 S2(10월 3일 지정)가 있을 때, **When** O의 권한이 박탈되면, **Then** 수락 절차 없이 S1이 A의 블로그장이 되고, O는 A의 일반 멤버로 남는다.
5. **Given** 부블로그장이 없는 블로그 B의 블로그장 P가, **When** 10월 2일 오후 3시에 강퇴되면, **Then** B는 10월 9일 04:00 폐쇄로 예약되고 "블로그장 권한 박탈로 인한 폐쇄 조치"로 공지되며, P를 제외한 멤버 전원과 구독자에게 10월 2일(즉시), 10월 6일 04:00(3일 전), 10월 8일 04:00(1일 전)에 폐쇄 예정 알림이 간다. 같은 알림이 같은 사람에게 두 번 가지 않는다. 블로그장이 없으므로 이 폐쇄 예정은 아무도 철회할 수 없다(D-94의 추론, 가정 참조).
6. **Given** 5번의 블로그 B가 폐쇄 예정 중일 때, **Then** B는 10월 9일 04:00까지 평소처럼 글쓰기·댓글이 된다.
7. **Given** 4번에서 S1이 블로그장이 된 뒤, **When** S1이 전 블로그장 O를 멤버로 두거나, 정지(3일·14일·30일·영구 중 하나)하거나, 강제 퇴장시키면, **Then** 그 조치는 블로그 단위 제재(BLG-13, `002-blog-management`)로 처리되고 메인 관리자는 관여하지 않는다.
8. **Given** 메인 관리자가, **When** 블로그장이 아닌 일반 멤버에게 경고·정지·강제 퇴장을 하려 하면, **Then** 그런 기능이 없어 할 수 없다(메인 관리자는 회원을 정지하지 않음).
9. **Given** 1~5번의 조치마다, **Then** 조치한 관리자, 시각, 종류(경고·강퇴·자동 위임·폐쇄 예약), 대상이 활동 기록에 남는다.
10. **Given** O가 블로그 A에서 받은 경고 2번 중 1번이 1년 넘게 지났을 때, **When** 메인 관리자가 A에서 경고를 하나 더 주면, **Then** A의 경고 수는 2번으로 세어 권한이 박탈되지 않는다(D-95).
11. **Given** O가 블로그 A와 C를 운영하고 A에서 경고 2번, C에서 경고 1번을 받았을 때, **Then** 경고는 블로그별로 세어 A는 2번, C는 1번이고 어느 블로그에서도 권한이 박탈되지 않는다(D-95).

### 사용자 스토리 4 - 블로그·블로그장 신고 처리 (우선순위: P2)

블로그 자체나 블로그장에 대한 신고(블로그장이 자기 블로그에 쓴 글·댓글 포함)와 메인 프로필에서 한 회원 신고는 메인 관리자에게 접수된다(D-93). 관리자는 신고를 확인하고 문제 없음, 블로그장 경고, 블로그장 강퇴, 블로그 폐쇄 중 하나로 처리하며, 결과는 신고한 회원에게 알림으로 간다.

**이 우선순위인 이유**: ADM-04는 우선순위 중이고, 처리 결과가 사용자 스토리 2·3의 조치로 이어진다.

**독립 테스트**: 블로그 신고, 블로그장 신고, 블로그장이 쓴 글 신고, 메인 프로필 회원 신고, 블로그 안의 멤버 글 신고를 하나씩 접수해 두고, 관리자 신고함에 앞의 네 건만 보이는지 확인한 뒤 네 가지 처리 결과를 각각 적용해 효과와 신고자 알림을 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 회원이 블로그 A 자체를 신고하고, 다른 회원이 A의 블로그장을 신고하고, 또 다른 회원이 A 안의 멤버 글을 신고했을 때, **When** 메인 관리자가 신고함을 열면, **Then** 블로그 신고와 블로그장 신고 2건만 보이고 멤버 글 신고는 보이지 않는다(그 신고는 A의 블로그장에게 접수됨).
2. **Given** 블로그 신고 1건을, **When** 관리자가 "문제 없음"으로 처리하면, **Then** 블로그와 블로그장에게 아무 조치도 가지 않고, 신고한 회원은 처리 결과 알림을 받는다.
3. **Given** 블로그장 신고 1건을, **When** 관리자가 "블로그장 경고"로 처리하면, **Then** 사용자 스토리 3의 경고와 같이 그 블로그장의 경고 수가 1 늘고, 이 경고로 3번이 되면 권한이 박탈된다.
4. **Given** 블로그장 신고 1건을, **When** 관리자가 "블로그장 강퇴"로 처리하면, **Then** 사용자 스토리 3의 4번 또는 5번과 같이 처리된다.
5. **Given** 블로그 신고 1건을, **When** 관리자가 "블로그 폐쇄"로 처리하면, **Then** 사용자 스토리 2의 강제 폐쇄와 같이 처리된다.
6. **Given** 신고한 회원이 알림 설정에서 "신고 처리 결과"를 꺼 두었을 때, **When** 관리자가 그 신고를 처리하면, **Then** 처리 결과 알림이 만들어지지 않는다. 처리 자체와 활동 기록은 그대로 남는다.
7. **Given** 블로그 A가 신고를 여러 번 받았을 때, **Then** 신고 수만으로 자동 조치되지 않고 관리자가 확인한 뒤에만 조치된다.
8. **Given** 회원이 A의 블로그장이 A에 쓴 댓글을 신고하고, 다른 회원이 메인 프로필에서 회원 U를 신고했을 때, **When** 메인 관리자가 신고함을 열면, **Then** 두 신고가 모두 보이고 A의 블로그장 신고함에는 보이지 않는다(D-93).

### 사용자 스토리 5 - 게시글·댓글 숨김·삭제와 복구 (우선순위: P2)

메인 관리자는 어느 블로그의 글이든 숨기거나 삭제하고, 댓글도 숨기거나 삭제한다. 남의 글을 수정할 수는 없다. 글을 삭제하면 작성자에게 알림이 가고, 실수나 잘못된 삭제는 30일 안에 관리자가 복구할 수 있다.

**이 우선순위인 이유**: ADM-03은 우선순위 중이다. 블로그장도 자기 블로그의 글을 삭제할 수 있어(D-58) 1차 대응은 블로그장이 하지만, 블로그장이 대응하지 않을 때 관리자가 내려야 한다(D-07).

**독립 테스트**: 서로 다른 블로그 두 곳에 글과 댓글을 만들어 두고, 관리자 계정으로 숨김·삭제·수정·복구를 각각 시도해 노출 여부, 작성자 알림, 활동 기록을 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 블로그 A의 멤버 M이 쓴 글이 있을 때, **When** 메인 관리자가 그 글을 숨기면, **Then** 그 글은 목록·검색·피드에 나오지 않고 활동 기록에 남는다.
2. **Given** 블로그 B의 글이 있을 때, **When** 메인 관리자가 그 글을 삭제하면, **Then** 그 글과 사진이 보이지 않게 되고, 작성자는 "운영" 탭의 "내 글 삭제됨" 알림을 받으며 이 알림은 끌 수 없다.
3. **Given** 어느 블로그의 글이든, **When** 메인 관리자가 내용을 수정하려 하면, **Then** 거부된다.
4. **Given** 10월 1일에 삭제된 글이 있을 때, **When** 메인 관리자가 10월 20일에 복구하면, **Then** 글이 다시 보이고 복구한 관리자·시각·대상이 활동 기록에 남는다. **When** 10월 31일(30일 뒤) 처리가 지난 뒤에는, **Then** 완전히 삭제되어 복구할 수 없다.
5. **Given** 댓글이 있을 때, **When** 메인 관리자가 숨기거나 삭제하면, **Then** 처리되고 활동 기록에 남는다.

### 사용자 스토리 6 - 관리자 활동 기록과 운영 기록 1년 보관 (우선순위: P2)

경고, 강퇴, 삭제, 폐쇄, 숨김, 복구, 신고 처리, "전체 보기" 같은 관리자 조치는 누가 언제 무엇을 했는지 모두 기록된다. 관리자 활동·신고·경고·정지 기록은 30일 규칙과 달리 1년 동안 보관된다.

**이 우선순위인 이유**: ADM-06은 우선순위 중이지만 SEC-09가 관리자 활동 기록을 요구하고, 경고 3번 누적(ADM-07)과 정지 3번 누적(BLG-13)을 세는 근거가 된다(D-60).

**독립 테스트**: 관리자 계정 두 개로 서로 다른 조치를 몇 가지 하고 활동 기록에서 조치자·시각·종류·대상이 모두 맞는지 확인한 뒤, 시각을 옮겨 30일 뒤와 1년 뒤에 기록이 남아 있는지 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 관리자 갑이 10월 2일 10:00에 블로그장 O에게 경고를 주고, 관리자 을이 10월 2일 11:00에 회원 U의 "전체 보기"를 눌렀을 때, **When** 활동 기록을 보면, **Then** 두 건이 조치자, 시각, 종류, 대상과 함께 남아 있다.
2. **Given** 10월 2일에 남은 관리자 활동 기록과 블로그장 경고 기록이 있을 때, **When** 30일이 지나면, **Then** 기록은 삭제되지 않고 그대로 남는다.
3. **Given** 블로그 안 신고 기록과 멤버 정지 기록(BLG-13)이 있을 때, **Then** 이 기록도 1년 동안 보관된다.
4. **Given** 10월 2일에 남은 관리자 활동 기록, 블로그장 경고 기록, 신고 기록이 있을 때, **When** 1년이 지난 뒤 첫 04:00 정리가 돌면, **Then** 그 기록들은 지워진다. **And** 영구 정지처럼 아직 효력이 있는 정지 기록은 풀릴 때까지 남는다(D-103 #19).

### 사용자 스토리 7 - 운영 통계 (우선순위: P3)

메인 관리자는 회원 수, 블로그 수, 일별 가입 수와 글 수를 본다.

**이 우선순위인 이유**: ADM-05는 우선순위 하이고, 다른 관리자 기능 없이도 서비스 운영은 된다.

**독립 테스트**: 날짜를 나눠 회원 가입과 글 작성을 미리 넣어 두고, 관리자 통계 화면의 숫자가 넣은 값과 같은지 확인하면 된다.

**인수 시나리오 (Acceptance Scenarios)**:

1. **Given** 10월 1일에 3명, 10월 2일에 5명이 가입하고 블로그 4개가 있을 때, **When** 메인 관리자가 통계를 보면, **Then** 회원 수 8, 블로그 수 4, 10월 1일 가입 3, 10월 2일 가입 5가 보인다(관리자 계정은 세지 않는다. 나중에 탈퇴한 회원은 회원 수에서 빠지지만 가입한 날의 가입 수에는 그대로 남는다, D-103 #21).
2. **Given** 10월 2일에 글 7개가 작성되었을 때, **When** 통계를 보면, **Then** 10월 2일 글 수 7이 보인다.
3. **Given** 일반 회원이, **When** 통계를 요청하면, **Then** 거부된다.

### 엣지 케이스 (Edge Cases)

- **폐쇄 예정 중 블로그장 강퇴**: 블로그장이 폐쇄 버튼을 눌러 7일 유예 중인 블로그에서 블로그장이 강퇴되는 경우, 부블로그장이 있어도 폐쇄 예정 중에는 위임할 수 없다는 규칙(BLG-08, D-20)과 자동 위임 규칙(ADM-07, D-17)이 부딪힌다. 부블로그장이 있으면 자동 위임하고 폐쇄 예정은 그대로 두며, 철회할지는 새 블로그장이 정한다(D-94). 부블로그장이 없으면 기존 폐쇄 예정 시각을 그대로 두고 강퇴 날짜 + 7일로 새로 잡지 않으며, 폐쇄 예정 알림도 다시 보내지 않는다(D-103 #14).
- **박탈로 폐쇄 예정인 블로그의 철회**: 부블로그장이 없어 박탈로 폐쇄 예정이 된 블로그에는 블로그장이 없다. 폐쇄 철회는 블로그장만 할 수 있고 메인 관리자는 관리자 폐쇄만 철회하므로(D-94, D-104), 이 폐쇄 예정은 철회할 수 없다(D-94의 추론, 가정 참조. `002-blog-management` 엣지 케이스와 같은 항목).
- **박탈 시 대기 중 위임 요청**: 블로그장이 보낸 위임 요청이 대기 중일 때 권한이 박탈되면, 요청한 사람이 더 이상 블로그장이 아니므로 요청을 자동 취소하고 요청을 받은 멤버에게 "위임 요청이 취소되었습니다" 알림(끌 수 없음)을 보낸다. 폐쇄 버튼 때(BLG-08)와 달리 다른 알림이 가지 않을 수 있어서다(D-103 #15).
- **폐쇄 예정 중 탈퇴**: 권한을 박탈당한 블로그장은 그 블로그의 일반 멤버로 남으므로(D-54), 다른 블로그의 블로그장이 아니면 회원탈퇴할 수 있다. 반대로 블로그장이 폐쇄 버튼을 눌러 7일 유예 중인 블로그가 있으면 그 사람은 아직 블로그장이라 탈퇴할 수 없다(USR-05, D-18). 메인 관리자는 회원을 강제 탈퇴시키지 않는다(D-44).
- **동시 처리**: 두 관리자가 경고 2번을 받은 블로그장에게 동시에 경고를 주어도, 경고 수는 정확히 늘고 권한 박탈과 자동 위임 또는 폐쇄 예약은 한 번만 일어나야 한다. 같은 신고를 두 관리자가 동시에 처리해도 처리 결과는 하나만 남아야 한다(ADM-04, ADM-07).
- **가입 여부·개인정보 노출 방지**: 관리자가 아닌 사람이 관리자 회원 검색을 요청하면 거부되고, 응답으로 어떤 이메일이 가입되어 있는지 알 수 없어야 한다(SEC-09, USR-02, D-28). 관리자 응답도 "전체 보기" 전에는 이메일·전화번호 원문을 담지 않는다(4.4, D-22).
- **여러 블로그를 운영하는 블로그장**: 한 회원은 공개(일부 공개 포함) 3개, 비공개 5개까지 블로그장일 수 있다(BLG-10). 블로그장 경고는 블로그별로 세므로, 한 블로그에서 3번째 경고를 받으면 그 블로그의 블로그장 권한만 박탈되고 그 사람이 운영하는 다른 블로그에는 영향이 없다. 한 블로그의 일로 다른 블로그 활동까지 막지 않는다(D-95, D-43).
- **블로그장이 바뀐 뒤의 경고 수**: 위임이나 자동 위임으로 새 블로그장이 된 회원의 경고 수는 이어받지 않고 0부터 센다. 경고는 그 블로그의 그 사람에게 준 것으로 세므로, 이전 블로그장이 나중에 다시 블로그장이 되면 1년 안의 자기 경고는 다시 센다(D-103 #13, D-95).
- **블로그장이 쓴 글에 대한 신고**: 블로그 안의 글·댓글 신고는 그 블로그의 블로그장에게 가지만(D-45), 블로그장 자신이 자기 블로그에 쓴 글·댓글이 신고되면 블로그장 대상 신고로 보아 메인 관리자에게 접수된다. 블로그장이 자기에 대한 신고를 직접 처리하지 않게 하기 위해서다(D-93, `003-social-notification` FR-024와 같은 항목).
- **자동 위임을 받는 부블로그장의 블로그 개수**: 가장 먼저 부블로그장이 된 사람이 이미 공개 블로그 3개를 운영하고 있어도 개수 제한(BLG-10)을 적용하지 않고 그 사람에게 넘긴다. 제한은 새로 만드는 수에 대한 것이고 일반 위임 수락에도 적용하지 않는다. 넘긴 뒤에는 제한 아래로 내려갈 때까지 새 블로그를 만들 수 없다(D-103 #16).
- **이미 폐쇄 예정이거나 숨겨진 블로그에 대한 신고**: 관리자는 신고를 처리할 수 있어야 한다. 강제 폐쇄 시점은 누른 날짜 + 7일 04:00으로 정해졌다(D-94). 이미 폐쇄 예정인 블로그에 "블로그 폐쇄"를 고르면 기존 폐쇄 예정 시각을 그대로 두고(늦추지 않음, 알림도 다시 보내지 않음) 폐쇄 사유만 관리자 폐쇄로 바꿔 기록한다. 그 뒤에는 블로그장이 철회할 수 없고 메인 관리자만 철회한다(D-103 #8, D-104).
- **탈퇴한 회원**: 탈퇴 후 30일 동안 개인정보는 보관되지만 화면에 보이지 않는다(4.5). 메인 관리자 회원 검색에도 탈퇴 후 30일 보관 중인 회원은 나오지 않고, 신고·경고 같은 운영 기록에서는 "탈퇴한 회원"으로 표시한다(D-103 #3). 탈퇴한 회원과 관련된 운영 기록은 1년 보관된다(4.5, D-60).
- **전화번호 중복(1차)**: 1차에는 전화번호 중복을 허용하므로(D-24) 전화번호로 회원을 찾으면 여러 계정이 나올 수 있다.
- **메인 관리자의 글 삭제와 블로그장의 글 삭제**: 둘 다 작성자에게 "내 글 삭제됨" 알림이 가고(3.6), 둘 다 남의 글을 수정할 수 없다(3.7, D-07, D-58). 블로그장의 삭제는 관리자 활동 기록 대상이 아니다.

## 요구사항 (Requirements) *(필수)*

### 기능 요구사항 (Functional Requirements)

#### 관리자 계정과 접근

- **FR-001**: 시스템은 메인 관리자 계정을 일반 회원과 분리하되, 별도 관리자 테이블을 두지 않고 회원과 같은 users 테이블에서 role = ADMIN으로 구분해야 하며, 관리자 페이지와 관리자 기능을 role = ADMIN인 계정만 쓸 수 있게 해야 한다. 관리자 계정은 메인 공지(BRD-10)와 관리 기능만 쓰고 블로그 활동을 하지 않는다(FR-004). 로그인 화면은 회원과 같고 잠금·사람 확인 규칙도 같다(SEC-03, SEC-13). 관리자 페이지는 `/admin` 주소에 따로 두어 role = ADMIN만 들어간다. 관리자 만들기 화면은 두지 않고, 서버 운영자가 블로그 활동이 없는 새 계정을 만들어 DB에서 role을 ADMIN으로 바꾼다. 회수도 role을 USER로 되돌리며, 다음 요청부터 거부된다(FR-002) (D-103 #1). [SEC-09, SEC-11, SEC-03, SEC-13, 3.5, D-90, D-103]
- **FR-002**: 시스템은 관리자 기능 요청마다 서버에서 요청자가 현재 메인 관리자인지 확인해야 하며, 로그인 정보(토큰)에 담긴 내용만 믿지 않고 권한이 회수된 계정의 요청은 다음 요청부터 거부해야 한다. [SEC-09, SEC-11, D-53]
- **FR-003**: 시스템은 비회원, 회원, 블로그 멤버, 블로그장(부블로그장 포함)의 관리자 기능 요청을 모두 거부하고, 거부 응답에 회원 정보나 가입 여부를 담지 않아야 한다. [SEC-09, SEC-11, 2장 기능별 권한, D-28]
- **FR-004**: 시스템은 메인 관리자 계정의 블로그 활동(블로그 생성, 참여 신청, 블로그에 글 쓰기, 댓글, 좋아요, 팔로우) 요청을 모두 거부해야 한다. 관리자는 블로그를 관리하는 역할이라 활동과 관리를 나누므로, 2장 기능별 권한 표의 메인 관리자 열에서 이 항목들은 X로 고쳤다(블로그에 글 쓰기는 "메인 공지만 (BRD-10)"). [2장 기능별 권한, SEC-09, BRD-10, D-90]

#### 회원 관리와 개인정보 보기

- **FR-005**: 시스템은 메인 관리자가 전체 회원을 검색하고 회원별 상세 정보를 볼 수 있게 해야 한다. 검색은 닉네임(일부만 맞아도 찾음)과 이메일(전체가 맞아야 찾음)로 하고 이름·전화번호 검색은 1차에 두지 않는다. 상세 정보에는 4.4 항목(FR-006대로 가림)과 가입일, 상태, 운영·참여 블로그, 블로그장 경고 이력(블로그별)을 넣는다(D-103 #2). 탈퇴 후 30일 보관 중인 회원은 검색에 나오지 않는다(D-103 #3). [ADM-01, 4.5, D-103]
- **FR-006**: 시스템은 메인 관리자에게 회원의 이메일·이름·닉네임·전화번호를 보여주되, 기본으로 이메일은 @ 앞의 처음 2글자만(@ 앞이 2글자 이하면 첫 글자만) 남기고 `***`로, 전화번호는 가운데 4자리를 `****`로 가려야 한다. 예: `abcdef@gmail.com` → `ab***@gmail.com`, `010-1234-5678` → `010-****-5678`. 이름은 가리지 않는다. 가리는 형식은 이메일·전화번호에만 정해져 있고(4.4), 블로그장 화면에서도 이름은 그대로 보이기 때문이다(D-103 #4). [4.4 메인 관리자 행, 4.4 가리는 형식, D-22, D-103]
- **FR-007**: 시스템은 가리는 처리를 서버가 응답을 만들 때 해야 하며, "전체 보기"를 누르기 전의 관리자 응답에는 이메일·전화번호 원문이 들어 있지 않아야 한다. [4.4, D-22]
- **FR-008**: 시스템은 메인 관리자가 "전체 보기"를 누르면 그 회원의 원래 이메일·전화번호를 보여주고, 누른 관리자·시각·대상 회원을 관리자 활동 기록에 남겨야 한다. 사유 입력은 받지 않고 누른 관리자·시각·대상 회원만 남긴다. "전체 보기"는 그 회원 한 명의 상세 화면에서 그 한 번만 원래 값을 보여 주고, 상세 화면을 다시 열면 다시 가린다. 회원 목록에는 "전체 보기"가 없다(D-103 #5). [4.4 메인 관리자 행, ADM-06, 4.6 보호 방법, D-103]
- **FR-009**: 시스템은 어느 관리자 화면에도 비밀번호 칸을 두지 않아야 한다. [4.4, D-22]
- **FR-010**: 시스템은 메인 관리자에게 회원 정지, 회원 강제 탈퇴, 블로그 멤버 경고·정지·강제 퇴장 기능을 제공하지 않아야 한다. 메인 관리자가 사람에게 하는 조치는 블로그장 경고와 블로그장 강퇴(권한 박탈)뿐이다. 개별 블로그의 참여 승인·멤버 강퇴도 하지 않는다(2장 기능별 권한 표의 메인 관리자 "참여 승인·멤버 강퇴"는 X로 고침, `002-blog-management` FR-038과 같은 항목). [ADM-01, 3.7, D-43, D-44, D-90]

#### 블로그 관리

- **FR-011**: 시스템은 메인 관리자가 공개 범위와 관계없이 전체 블로그를 검색하고, 블로그마다 블로그장, 멤버 수, 글 수를 볼 수 있게 해야 한다. 검색은 이름·주소·블로그장 닉네임으로 하고, 공개 범위와 관계없이 운영 중·폐쇄 예정·폐쇄됨(30일 보관 중)·숨김 블로그를 모두 상태와 함께 보여 주며 상태로 걸러 볼 수 있게 한다(D-103 #6). [ADM-02, 3.5, D-103]
- **FR-012**: 시스템은 메인 관리자가 블로그를 숨길 수 있게 하고, 숨긴 블로그는 메인 목록·검색·피드에 나오지 않게 해야 한다. 숨긴 블로그는 멤버가 아닌 사람(비회원·구독자 포함)이 주소나 공유 링크로도 들어갈 수 없게 하고, 블로그장·멤버는 평소처럼 보고 글을 쓰게 한다. 관리자는 숨김을 풀 수 있고, 숨길 때와 풀 때 모두 활동 기록에 남긴다. 숨길 때 블로그장에게 "운영" 탭 알림(끌 수 없음)을 보내고 멤버에게는 보내지 않는다(D-103 #7). [ADM-02, 6.1, D-103]
- **FR-013**: 시스템은 메인 관리자가 블로그를 강제 폐쇄할 수 있게 하고, 블로그장 폐쇄(BLG-09)와 같이 누른 날짜 + 7일의 04:00(한국 시간)에 폐쇄되도록 예약하며, 블로그장을 제외한 멤버 전원과 구독자에게 즉시·3일 전·1일 전 폐쇄 예정 알림을 보내야 한다. 폐쇄 예정 기간에는 평소처럼 운영하고, 관리자 폐쇄의 철회는 메인 관리자만 할 수 있게 해야 한다(블로그장은 철회할 수 없음). 관리자가 철회하면 운영 중으로 돌리고 블로그장 철회와 같은 철회 알림을 보내며, 관리자 폐쇄가 아닌 폐쇄 예정은 관리자가 철회할 수 없다. [ADM-02, 3.7, BLG-09, D-12, D-94, D-104, `002-blog-management` FR-084]
- **FR-014**: 시스템은 강제 폐쇄된 블로그의 글·사진·카테고리를 폐쇄된 날부터 화면에 보이지 않게 하고 30일 뒤 완전히 삭제해야 하며, 블로그 주소는 30일 뒤에 다른 블로그가 쓸 수 있게 해야 한다. [4.5, BLG-09, D-35, D-40]

#### 게시글·댓글 관리

- **FR-015**: 시스템은 메인 관리자가 어느 블로그의 글과 댓글이든 숨기거나 삭제할 수 있게 해야 한다. [ADM-03, 2장 기능별 권한, BRD-01, 3.7 글 삭제]
- **FR-016**: 시스템은 메인 관리자를 포함해 작성자가 아닌 누구도 남의 글을 수정하지 못하게 해야 한다. [BRD-01, 3.7 글 삭제, D-07, D-58]
- **FR-017**: 시스템은 메인 관리자가 글을 삭제하면 작성자에게 "운영" 탭의 "내 글 삭제됨" 알림을 보내야 하며, 이 알림은 끌 수 없어야 한다. 글을 숨기면 작성자에게 "운영" 탭의 "내 글 숨겨짐" 알림(끌 수 없음)을 보내고, 댓글을 숨기거나 삭제할 때는 알리지 않는다(D-103 #9). [BRD-01, 3.6, 2장 회원 표, D-103]
- **FR-018**: 시스템은 숨긴 글을 목록·검색·피드에서 빼야 한다. 숨긴 글은 작성자 본인에게만 "관리자가 숨긴 글" 표시와 함께 보이고, 그 블로그의 블로그장을 포함한 다른 사람에게는 보이지 않는다. 관리자는 숨김을 풀 수 있다. 숨김은 기간 없이 그대로 두어 30일 뒤 지우지 않고, 삭제만 30일 뒤 완전히 삭제한다(D-103 #10). [ADM-03, 6.1 결과에서 제외, 4.5, D-103]
- **FR-019**: 시스템은 삭제된 글·댓글·사진을 삭제한 날부터 30일 동안 보이지 않게 보관하고, 그 동안 메인 관리자가 복구할 수 있게 하며, 30일 뒤에는 완전히 삭제해 복구할 수 없게 해야 한다. 복구 대상은 관리자·블로그장이 지운 글·댓글·사진이고, 작성자가 스스로 지운 것은 복구하지 않는다. 글을 복구하면 작성자에게 "운영" 탭 알림을 보낸다(D-103 #11). [4.5, D-40, D-103]

#### 블로그장 경고와 강퇴(권한 박탈)

- **FR-020**: 시스템은 메인 관리자가 블로그장에게 경고를 줄 수 있게 하고, 경고를 받은 블로그장에게 "운영" 탭의 "블로그장 경고" 알림을 보내야 하며, 이 알림은 끌 수 없어야 한다. 경고 사유는 필수(1~500자, 설정값)이고, 알림에 사유와 지금 경고 수(예: 3번 중 2번)를 넣으며 신고자는 넣지 않는다(D-103 #12). [ADM-07, 3.6, 3.7 경고, D-103]
- **FR-021**: 시스템은 블로그장이 받은 경고 수를 블로그별로 세어, 그 블로그에서 경고가 3번이 되는 순간 그 블로그의 블로그장 권한을 박탈해야 한다. 1년이 지난 경고는 횟수에서 빼야 하며, 경고 2번 이하로는 권한을 박탈하지 않아야 한다(FR-022의 바로 강퇴 제외). 블로그장이 바뀌면 새 블로그장의 경고 수는 0부터 센다. 경고는 그 블로그의 그 사람에게 준 것으로 세므로, 이전 블로그장이 다시 블로그장이 되면 1년 안의 자기 경고를 다시 센다(D-103 #13). [ADM-07, 3.7, D-30, D-95, D-103]
- **FR-022**: 시스템은 메인 관리자가 경고 수와 관계없이 블로그장을 바로 강퇴(권한 박탈)할 수 있게 해야 한다. [ADM-07, ADM-01, 3.7 내보내기, D-44]
- **FR-023**: 시스템은 블로그장 권한을 박탈할 때 그 블로그에 부블로그장이 있으면, 부블로그장이 된 시각이 가장 이른 사람에게 받는 사람의 수락 절차 없이 블로그장을 넘겨야 한다. [ADM-01, ADM-07, D-17, D-30]
- **FR-024**: 시스템은 블로그장 권한을 박탈할 때 그 블로그에 부블로그장이 없으면, 박탈한 날짜 + 7일의 04:00(한국 시간)에 폐쇄되도록 예약하고, 블로그장 폐쇄(BLG-09)와 같은 대상(박탈된 사람을 제외한 멤버 전원과 구독자)과 시점(즉시, 3일 전, 1일 전)에 폐쇄 예정 알림을 보내며, "블로그장 권한 박탈로 인한 폐쇄 조치"라고 공지해야 한다. 같은 알림은 한 사람에게 두 번 가지 않아야 한다. 이 공지는 폐쇄 예정 알림 문구에 넣어 알리고, 블로그장이 없으므로 블로그 화면의 공지 글은 따로 쓰지 않는다(D-103 #17). [ADM-07, ADM-01, D-12, D-13, D-14, D-17, D-30, BLG-09, D-103]
- **FR-025**: 시스템은 FR-024로 폐쇄 예정이 된 블로그를 폐쇄 시각까지 평소처럼 운영해 글쓰기·댓글이 되게 해야 한다. [D-67, BLG-09]
- **FR-026**: 시스템은 권한을 박탈당한 블로그장을 그 블로그의 일반 멤버로 남겨야 하며, 그 사람을 멤버로 둘지, 정지할지, 강제 퇴장시킬지는 새 블로그장이 블로그 단위 제재(BLG-13)로 정하게 해야 한다. 메인 관리자는 이 판단에 관여하지 않는다. [ADM-07, D-54, D-43, D-44]
- **FR-027**: 시스템은 권한을 박탈당한 블로그장에게 "운영" 탭의 "권한 박탈" 알림을 보내야 하며, 이 알림은 끌 수 없어야 한다. [3.6, ADM-07]
- **FR-028**: 시스템은 블로그장 권한 박탈과 그에 따른 자동 위임 또는 폐쇄 예약을 한 번의 조치로 처리해, 여러 관리자가 동시에 경고하거나 강퇴해도 박탈·위임·폐쇄 예약이 한 번만 일어나게 해야 한다. [ADM-07, ADM-06]
- **FR-029**: 시스템은 블로그장이 폐쇄 버튼을 눌러 이미 폐쇄 예정인 블로그(위임 불가, D-20)에서 권한을 박탈할 때, 부블로그장이 있으면 자동 위임하고 폐쇄 예정은 그대로 두며(철회할지는 새 블로그장이 정함, D-94), 부블로그장이 없으면 기존 폐쇄 예정 시각을 그대로 두고 새로 잡지 않으며 폐쇄 예정 알림도 다시 보내지 않아야 한다(D-103 #14). 권한을 박탈할 때 블로그장이 보낸 위임 요청이 대기 중이면 자동 취소하고, 요청을 받은 멤버에게 "위임 요청이 취소되었습니다" 알림(끌 수 없음)을 보내야 한다(D-103 #15). 박탈로 폐쇄 예정이 된 블로그(FR-024)는 블로그장이 없으므로 철회할 수 없다(D-94의 추론, 가정 참조). [ADM-07, BLG-08, BLG-09, D-17, D-20, D-94, D-103]

#### 신고 처리

- **FR-030**: 시스템은 블로그 자체와 블로그장에 대한 신고(블로그장이 자기 블로그에 쓴 글·댓글 신고 포함)와 메인 프로필에서 한 회원 신고만 메인 관리자에게 접수하고, 블로그 안의 그 밖의 회원·글·댓글 신고는 메인 관리자에게 접수하지 않아야 한다. [ADM-04, SOC-06, 3.7 신고 처리, D-45, D-93]
- **FR-031**: 시스템은 메인 관리자가 접수된 신고를 확인하고 문제 없음, 블로그장 경고, 블로그장 강퇴, 블로그 폐쇄 중 하나로 처리하게 해야 하며, 블로그장 경고는 FR-020·FR-021, 블로그장 강퇴는 FR-022~FR-029, 블로그 폐쇄는 FR-013·FR-014와 같은 효과를 내야 한다. [ADM-04, ADM-07, ADM-02, D-38, D-44]
- **FR-032**: 시스템은 신고 수만으로 블로그나 블로그장을 자동으로 제재하지 않고, 메인 관리자가 확인해 처리한 결과로만 조치해야 한다. [ADM-04]
- **FR-033**: 시스템은 메인 관리자가 신고를 처리하면 신고한 회원에게 "운영" 탭의 "신고 처리 결과" 알림을 보내야 하며, 회원은 이 알림을 끌 수 있어야 한다. [ADM-04, 3.6, SOC-04]
- **FR-034**: 시스템은 한 신고에 처리 결과가 하나만 남게 해야 하며, 이미 처리된 신고를 다른 관리자가 다시 처리하지 못하게 해야 한다. 처리 결과는 1차에는 나중에 바꾸거나 다시 검토할 수 없고, 같은 대상에 새 신고가 오면 새로 처리한다(D-103 #18). [ADM-04, D-103]

#### 제재 권한의 경계 (3.7)

- **FR-035**: 시스템은 3.7 표에 따라 메인 관리자의 제재 대상을 블로그장과 블로그로, 블로그장(멤버 관리 권한을 받은 부블로그장 포함)의 제재 대상을 자기 블로그의 멤버로 나눠야 하며, 어느 쪽도 자기 범위 밖의 제재를 할 수 없어야 한다. [3.7 제재 대상, SEC-07, D-43, D-44]
- **FR-036**: 시스템은 정지 기간 선택지를 3일, 14일, 30일, 영구로 두고, 정지는 기간이 끝나거나 정지를 준 사람이 해제하면 풀리게 해야 한다. 메인 관리자는 회원을 정지하지 않으므로 이 선택지는 블로그 단위 정지(BLG-13)에만 쓰인다. [3.7 정지 기간, D-57, D-44]
- **FR-037**: 시스템은 블로그 안의 멤버 경고·정지·강제 퇴장, 블로그 안 신고 처리, 정지 3번 누적 표시, 강제 퇴장 시 블랙리스트 등록을 `002-blog-management` 명세(FR-048~FR-056)대로 처리하고, 이 명세의 관리자 기능에 넣지 않아야 한다. [BLG-13, BLG-11, 3.7, D-43, D-45, D-46]

#### 관리자 활동 기록과 운영 기록 보관

- **FR-038**: 시스템은 관리자 활동 기록, 신고 기록, 경고 기록(블로그장 경고, 멤버 경고), 정지 기록을 30일 삭제 규칙에서 빼고 1년 동안 보관해야 한다. 신고 기록에는 신고 대상(대상 종류 + 대상 번호)과 신고 당시 대상의 내용을 함께 저장해, 대상 글·댓글이 30일 뒤 지워져도 분쟁 때 확인할 수 있게 해야 한다. 1년은 기록이 생긴 날(조치·신고한 날)부터 세고, 1년이 지난 기록은 04:00 정리에서 지운다(경고·정지 횟수에서 1년 지난 것을 빼는 D-95와 같은 기준). 영구 정지처럼 아직 효력이 있는 정지 기록은 풀릴 때까지 남긴다. 탈퇴 후 30일이 지나 개인정보를 지운 회원의 기록에는 회원 번호만 남기고 "탈퇴한 회원"으로 표시하며, 신고 당시 내용(D-85)은 그대로 1년 보관한다(D-103 #19). [4.5 30일 규칙의 예외, D-60, D-40, D-85, D-95, D-103]
- **FR-039**: 시스템은 메인 관리자의 모든 조치(블로그장 경고, 블로그장 강퇴, 자동 위임, 폐쇄 예약, 블로그 숨김, 강제 폐쇄, 글·댓글 숨김·삭제, 복구, 신고 처리, "전체 보기")를 조치한 관리자, 시각, 종류, 대상과 함께 관리자 활동 기록에 남겨야 한다. 활동 기록은 모든 메인 관리자가 볼 수 있고(관리자 등급은 두지 않음), 고치거나 지우는 기능은 두지 않으며, 1년 지난 기록만 04:00 정리가 지운다(D-103 #20). [ADM-06, SEC-09, 3.5, 4.4, D-103]

#### 통계

- **FR-040**: 시스템은 메인 관리자에게 회원 수, 블로그 수, 일별 가입 수, 일별 글 수를 보여줘야 한다. 회원 수는 탈퇴하지 않은 회원(관리자 계정 제외), 블로그 수는 운영 중·폐쇄 예정 블로그(숨김 포함, 폐쇄된 것 제외)를 센다. 일별 가입·글 수는 그날 생긴 수를 그대로 세어 나중에 탈퇴·삭제돼도 센다. 일별 통계는 최근 30일(설정값)을 보여준다(D-103 #21). [ADM-05, D-68, D-103]

### 핵심 엔터티 (Key Entities) *(데이터를 다루는 경우 포함)*

- **메인 관리자**: 관리자 페이지와 관리자 기능을 쓸 수 있는 계정. 별도 관리자 테이블 없이 회원과 같은 users 테이블에서 role = ADMIN으로 구분하며, 블로그 활동을 하지 않고 메인 공지(BRD-10)와 관리 기능만 쓴다(D-90). 관리자 권한(role = ADMIN), 권한을 받은 시각, 권한 회수 여부. (만들고 회수하는 방식은 FR-001 참조)
- **관리자 활동 기록**: 메인 관리자가 한 조치 한 건. 조치한 관리자, 시각, 종류(블로그장 경고, 블로그장 강퇴, 자동 위임, 폐쇄 예약, 블로그 숨김, 강제 폐쇄, 글·댓글 숨김·삭제, 복구, 신고 처리, "전체 보기"), 대상(회원·블로그·글·댓글·신고), 관련 신고. 1년 보관한다.
- **블로그장 경고**: 메인 관리자가 블로그장에게 준 경고. 대상 블로그장, 블로그, 경고한 관리자, 사유(1~500자, D-103 #12), 시각, 관련 신고(있으면). 1년 보관하며 경고 3번 누적의 근거가 된다. 경고 수는 블로그별로 세고 1년이 지난 경고는 뺀다(D-95).
- **블로그장 권한 박탈**: 블로그, 박탈된 회원, 원인(경고 3번 누적 또는 바로 강퇴), 시각, 결과(자동 위임받은 부블로그장 또는 폐쇄 예정 시각).
- **블로그(관리 관점)**: `002-blog-management`의 블로그에 더해 숨김 여부, 숨긴 시각·관리자, 폐쇄 사유(블로그장 폐쇄, 블로그장 권한 박탈, 관리자 강제 폐쇄). 관리자 화면에서는 블로그장, 멤버 수, 글 수를 함께 본다.
- **블로그·블로그장 신고**: 신고한 회원, 대상(블로그, 블로그장, 블로그장이 자기 블로그에 쓴 글·댓글, 메인 프로필에서 신고한 회원, D-93. 대상 종류 + 대상 번호로 가리킴), 신고 당시 대상 내용(D-85), 사유, 접수 시각, 처리 상태, 처리 결과(문제 없음·블로그장 경고·블로그장 강퇴·블로그 폐쇄), 처리한 관리자, 처리 시각. 1년 보관한다.
- **글·댓글 상태(관리 관점)**: 보임·숨김·삭제, 숨기거나 삭제한 사람, 시각. 삭제는 30일 동안 복구할 수 있다.
- **회원 정보 보기(관리 관점)**: 이메일·이름·닉네임·전화번호. 기본은 이메일·전화번호를 가린 값이고, "전체 보기" 때만 원래 값을 준다. 비밀번호는 없다.
- **운영 통계**: 회원 수, 블로그 수, 날짜별 가입 수, 날짜별 글 수.

## 성공 기준 (Success Criteria) *(필수)*

### 측정 가능한 결과 (Measurable Outcomes)

- **SC-001**: 관리자 회원 검색·블로그 검색·신고함 목록은 목표 1초, 늦어도 2초 안에 응답하고, 5초를 넘기면 기다리게 두지 않고 중단한 뒤 다시 시도하라는 안내를 보여준다. [4.2, D-48]
- **SC-002**: 메인 관리자가 아닌 계정(블로그장 포함)과 비회원의 관리자 기능 요청은 100% 거부되고, 관리자 권한을 회수한 계정은 다음 요청부터 100% 거부된다. [SEC-09, SEC-11]
- **SC-003**: "전체 보기"를 누르기 전의 관리자 응답에 이메일·전화번호 원문이 들어간 경우가 0건이고, "전체 보기"를 누른 경우의 100%가 관리자·시각·대상과 함께 기록된다. [4.4, ADM-06, D-22]
- **SC-004**: 메인 관리자의 조치 100%가 조치자·시각·종류·대상과 함께 활동 기록에 남고, 운영 기록(관리자 활동·신고·경고·정지)이 1년이 되기 전에 삭제된 경우가 0건이다. [ADM-06, 4.5, D-60]
- **SC-005**: 경고 3번째에 권한이 박탈되지 않은 경우와 경고 2번 이하에서 자동 박탈된 경우가 모두 0건이고, 두 관리자가 동시에 경고를 10번 반복해 주는 테스트에서도 박탈·자동 위임·폐쇄 예약은 블로그당 한 번만 일어난다. [ADM-07, D-30]
- **SC-006**: 권한 박탈 시 부블로그장이 있으면 100% 가장 먼저 부블로그장이 된 사람에게 넘어가고, 없으면 100% 박탈한 날짜 + 7일의 04:00(한국 시간)에 폐쇄되며, 대상자 1명당 폐쇄 예정 알림은 정확히 3번(즉시·3일 전·1일 전) 가고 중복 발송은 0건이다. [ADM-07, D-12, D-13, D-14, D-17]
- **SC-007**: 블로그 안의 회원·글·댓글 신고(블로그장과 블로그장이 쓴 글·댓글 대상 제외)가 메인 관리자 신고함에 들어간 경우와, 블로그장 대상 신고가 그 블로그장 신고함에 들어간 경우가 0건이고, 메인 관리자가 처리한 신고의 100%에서 신고자(알림을 켠 경우)에게 처리 결과 알림이 간다. [ADM-04, D-45, 3.6]
- **SC-008**: 메인 관리자의 남의 글 수정 성공이 0건이고, 메인 관리자가 회원을 정지하거나 블로그 멤버를 강제 퇴장시킨 경우와 메인 관리자 계정의 블로그 활동(블로그 생성, 참여 신청, 글쓰기, 댓글, 좋아요, 팔로우) 요청이 성공한 경우가 0건이다. [D-07, D-44, D-90, 3.7]
- **SC-009**: 숨기거나 삭제한 글과 숨긴 블로그가 메인 목록·검색 결과·피드에 나온 경우가 0건이고, 삭제 후 30일 안의 복구 요청은 100% 성공하며 30일 뒤에는 0건 성공한다. [ADM-02, ADM-03, 6.1, 4.5]
- **SC-010**: 관리자 페이지의 회원 조회, 블로그 조회, 신고 처리, 통계 화면을 PC와 모바일 화면에서 모두 쓸 수 있다. [4.2]

## 가정 (Assumptions)

- **1차 범위**: 서버 1대로 운영하되 서버를 늘려도 코드를 거의 고치지 않도록 관리자 권한, 경고 수, 활동 기록 같은 상태를 서버 메모리에 두지 않는다(4.3, SCL-01). 박탈로 인한 7일 뒤 04:00 폐쇄와 3일 전·1일 전 알림은 블로그장 폐쇄(BLG-09)와 같은 매일 04:00 처리를 쓰고, 처음부터 여러 서버에서 한 번만 실행되게 만든다(SCL-03, D-12).
- **1차 전화번호 중복 허용**: 1차에는 전화번호 중복을 허용하고, 문자 인증을 넣는 2차에 한 번호 한 계정으로 바꾼다(USR-01, D-24). 1차에는 전화번호로 회원을 찾으면 여러 계정이 나올 수 있다.
- **메인 관리자의 역할 범위**: 메인 관리자는 블로그와 블로그장만 관리하고, 회원은 검색·조회만 한다(2장, 3.5, D-44). 블로그 멤버 관리는 블로그장이 블로그 단위로 한다(D-43). 메인 관리자 계정은 블로그 활동을 하지 않고 메인 공지(BRD-10)와 관리 기능만 쓴다(D-90).
- **박탈 후 폐쇄 예정의 철회(추론)**: D-94는 폐쇄 철회를 블로그장만 할 수 있다고 정했다. 블로그장 권한 박탈 후 부블로그장이 없어 폐쇄 예정이 된 블로그(ADM-07)는 블로그장이 없으므로 철회할 사람이 없는 것으로 읽었다. 이 부분은 결정 문서에 명시된 것이 아니라 D-94에서 추론한 것이므로 다르면 고친다(FR-024, FR-029).
- **결정의 선후**: D-38(신고 처리 결과: 문제 없음·경고·정지·강제 퇴장)은 D-43·D-44·D-45로 범위가 나뉘기 전의 결정이다. 메인 관리자 쪽 처리 결과는 ADM-04의 네 가지(문제 없음·블로그장 경고·블로그장 강퇴·블로그 폐쇄)를 따르고, 정지는 블로그장 쪽(BLG-13)에만 있다.
- **범위 밖**: 신고 접수 화면과 신고 사유·2주 중복 제한(SOC-06, `003-social-notification`), 알림 전달·알림 설정(SOC-04, 3.6, `003-social-notification`), 메인 공지사항 작성(BRD-10, `004-board`), 글 삭제의 게시판 쪽 동작(BRD-01, `004-board`), 블로그 단위 제재·블랙리스트(BLG-11~13, `002-blog-management`)는 각 명세에서 다룬다. 이 명세는 그 기능과 메인 관리자의 경계와 관리자 조치의 결과만 정한다.
- **개인정보**: 실제 서비스로 공개하기 전에 법률 검토를 받는 것을 권한다(4.6). 관리자 열람 기록은 개인정보 보호 방법의 하나다(4.6).
- **시간대**: 모든 날짜·시각(폐쇄 예정 시각, 3일 전·1일 전, 30일, 1년, 일별 통계)은 한국 시간 기준이다(7장 폐쇄 처리).
- **DB 설계**: 엔터티의 물리 설계(ERD)는 요구사항 정리 뒤에 한다(D-47).
- **의존 기능**: 회원 계정과 로그인(USR-01~05, SEC-04, `001-member-auth`), 블로그·블로그 역할·부블로그장 지정 시각·폐쇄 처리(BLG-01~13, `002-blog-management` FR-043·FR-082), 알림(SOC-04, 3.6, 30초마다 확인 D-72), 신고 접수(SOC-06), 글·댓글(BRD-01, BRD-06), 통합 검색(BRD-08)과 메인 피드(BRD-09)의 숨김 제외.
- **기술 선택(plan.md에서 다룸)**: 인증·인가는 Spring Security로 하고 주소 단위로 비회원·회원·관리자를 나눈다(SEC-11, D-09). 로그인은 JWT + HttpOnly 쿠키이며 토큰에는 회원 번호 정도만 담고 권한은 요청마다 DB에서 확인한다(D-53). 매일 04:00 처리는 `@Scheduled(cron = "0 0 4 * * *", zone = "Asia/Seoul")` + ShedLock(D-12, SCL-03), 폐쇄 알림 종류는 `BLOG_CLOSING`(7장 폐쇄 처리)이다.
