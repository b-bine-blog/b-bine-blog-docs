# 002 블로그 관리 조사 (Phase 0 Research)

**날짜**: 2026-10-08 | **명세**: [spec.md](spec.md) | **계획**: [plan.md](plan.md)

명세의 확인 필요 항목은 D-98로 모두 정해졌다. 여기서는 001에서 정한 기술(R-01~R-14, `specs/001-member-auth/research.md`)을 그대로 쓰고, 002에서 새로 생기는 구현 방식만 정한다.
규칙 값(개수·기간)은 명세·결정을 그대로 따르고 여기서 새로 정하지 않는다. 아래 "가정"으로 표시한 것은 문서에 없어 구현 기본값으로 둔 것이며, 사용자 확인 뒤 바뀔 수 있다.

## R-01 블로그별 역할 확인 방식

- **결정**: `BlogPermissionService`가 요청마다 `blog_members`에서 (blog_id, user_id) 한 행을 읽어 역할과 권한 3개를 확인한다. 컨트롤러 메서드에 `@PreAuthorize("@blogAuth.has(#blogId, 'MEMBER_MANAGE')")` 형식으로 붙인다. 권한 이름은 `VIEW`, `MEMBER`, `BLOG_INFO`, `MEMBER_MANAGE`, `POST_MANAGE`, `OWNER` 6개다. 블로그장은 모든 권한을 가진다. 부블로그장은 켜진 체크박스 권한만, 멤버는 `MEMBER`까지만 가진다.
- **정지 확인**: `VIEW` 이상 모든 권한 확인에서 그 블로그의 진행 중 정지가 있으면 403 `BLOG_SUSPENDED`(정지 종료 시각·사유 포함)로 거부한다. 진행 중 정지는 "가장 최근 SUSPEND가 아직 끝나지 않았고(ends_at NULL 또는 미래), 그 뒤에 UNSUSPEND가 없음"이다.
- **이유**: SEC-07, SEC-11, D-09, D-53. 토큰에는 회원 번호만 있으므로(001 R-03) 정지·강퇴·위임·권한 변경이 다음 요청부터 바로 반영된다(FR-036).
- **검토한 다른 안**: 역할을 토큰이나 세션에 캐시(반영이 늦어 헌장 II 위반), 서비스 안에서만 확인(빠뜨리기 쉬워 컨트롤러 선언과 서비스 확인을 둘 다 둔다).

## R-02 생성 개수 제한과 동시 요청

- **결정**: 블로그 생성과 공개 범위 변경은 같은 트랜잭션 안에서 `SELECT ... FROM users WHERE id = ? FOR UPDATE`로 회원 행을 먼저 잠근다. 그 뒤 그 회원이 블로그장인 `ACTIVE`·`CLOSING` 블로그를 공개(PUBLIC+LINK)·비공개로 나눠 센다. 제한값은 `blog.limit.public=${BLOG_LIMIT_PUBLIC:3}`, `blog.limit.private=${BLOG_LIMIT_PRIVATE:5}`이고, 공개 제한은 시작할 때 1~5 범위를 확인한다.
- **이유**: D-68이 회원 행 DB 잠금을 정했다. DB 잠금이라 서버가 여러 대여도 같게 동작한다(SCL-01).
- **세는 대상**: 위임받은 블로그도 지금 블로그장이므로 센다(FR-013 "블로그장인 블로그" 기준). *가정*: "만든 개수"를 지금 블로그장인 블로그 수로 읽었다.
- **검토한 다른 안**: 애플리케이션 락(서버가 늘면 깨짐), 낙관적 잠금 재시도(제한 초과를 막으려면 카운터 컬럼이 따로 필요).

## R-03 블로그 주소

- **결정**: 주소는 `^[a-z0-9-]{3,30}$`로 검사한다. 예약어 목록은 설정값 `blog.address.reserved`에 둔다(기본: main, admin, api, login, signup, search). 중복은 DB의 `uk_blogs_address`로 막고, 제약 위반은 409 `BLOG_ADDRESS_TAKEN`으로 바꾼다. 동시에 같은 주소로 만들면 하나만 성공한다.
- **폐쇄 주소**: 폐쇄된 블로그는 30일 뒤 정리 때까지 주소를 그대로 가지고 있으므로 유니크 제약이 재사용을 막는다. 정리 때 `address = NULL`로 비운다(D-86).
- **블로그 화면 경로**: `/blog/{주소}`와 그 아래 경로는 `BlogPageController`가 `static/blog/index.html`(블로그 홈)이나 `static/blog/manage.html`(운영)로 forward한다. API는 `/api/blogs/...`라 겹치지 않는다. 블로그 만들기 화면은 `/blogs/new.html`에 두어 `/blog/` 아래에 화면 단어가 생기지 않게 한다. 그래서 추가 예약어는 지금은 없다(FR-004).
- **API에서 블로그 지정**: 주소는 숫자만으로도 될 수 있어 `/api/blogs/{blogId}`와 겹친다. 그래서 관리 API는 블로그 번호를 쓰고, 화면이 처음 한 번 `GET /api/blogs/address/{address}`로 번호를 얻는다.

## R-04 블로그 태그

- **결정**: 6.4 규칙을 `common/tag/TagNormalizer`로 만든다. 앞의 `#`과 앞뒤 공백을 빼고, 가운데 공백은 `_`로 바꾸고, 영문은 소문자로 만든다. 1~20자 한글·영문·숫자·`_`만 허용하고, 같은 태그는 합친다. 블로그 태그는 최대 10개(`blog.tag.max-count`)다. `tags` 행은 이름으로 찾고 없으면 만든다(동시 생성은 `uk_tags_name` 위반을 잡아 다시 읽음). 이 클래스는 004 글 태그에서도 그대로 쓴다.
- **이유**: FR-001, D-88, D-96(금칙어 없음).

## R-05 대표 이미지

- **결정**: 001의 `ImageValidator`와 `ImageSanitizer`, `FileStorage`를 그대로 쓴다. `images.owner_type = 'BLOG_COVER'`, `owner_id = blogs.id`로 저장하고, 블로그 생성(JSON)과 따로 `PUT /api/blogs/{blogId}/cover-image`(multipart)로 올린다. 화면은 생성 응답을 받은 뒤 이미지를 올린다. 바꾸거나 지운 이미지는 `deleted_at`을 채우고, 30일 뒤 04:00 정리에서 파일과 행을 지운다(프로필 사진과 같음).
- **이유**: FR-007, 6.3, D-75. 생성 요청을 JSON 하나로 두면 검증 오류 응답이 단순해진다.

## R-06 공개 범위와 공유 링크

- **열람 판단** (`BlogAccessPolicy`):
  - CLOSED: 404
  - PUBLIC: 누구나
  - LINK: 멤버, 구독자, 그 블로그의 유효한 공유 링크 쿠키가 있는 사람
  - PRIVATE: 멤버만
  - 모든 경우에 로그인한 회원이 그 블로그에서 정지 중이면 403
- **공유 링크**: 32바이트 무작위 값을 base64url(43자)로 만든다. `blog_share_links`에 블로그당 `active = true`인 행은 하나뿐이고, 새로 만들면 이전 행을 `active = false`로 바꾼다. 링크 형식은 `/blog/{주소}?share={값}`이다. 화면이 `POST /api/blogs/share-access`에 값을 보내면 서버가 확인하고 `BLOG_SHARE_{blogId}` 쿠키(HttpOnly, Secure, SameSite=Lax, 세션 쿠키)를 굽는다. 이후 요청은 이 쿠키로 열람을 판단하므로 서버에 상태가 없다(SCL-01). 링크를 다시 만들면 쿠키 값이 더 이상 유효한 링크와 맞지 않아 바로 막힌다(FR-028).
- **공개 범위 변경** (블로그장만):
  - LINK로 바꾸면 새 링크를 만든다.
  - LINK에서 벗어나면 유효한 링크를 막는다.
  - PUBLIC·LINK에서 PRIVATE로 바꾸면 구독자 전원에게 끌 수 없는 `BLOG_PRIVATE` 알림을 보낸다.
  - 구독은 지우지 않는다(FR-031, FR-032).
- **숨김 블로그** (`hidden = true`): 목록·검색에서 뺀다. 숨김 블로그에 들어가는 규칙은 관리자 명세(005)에서 정하므로, 002에서는 열람을 막지 않는다. *가정*

## R-07 목록과 검색

- **목록**: `status IN ('ACTIVE','CLOSING') AND visibility = 'PUBLIC' AND hidden = false` 조건이다.
  - 최신순은 `created_at DESC, id DESC`이다.
  - 인기순은 `member_count DESC, created_at DESC`이고, 기존 인덱스 2개를 쓴다.
  - 페이지 크기는 10·20·30 중 하나이고 기본은 10이다. 다른 값은 400이다.
  - 폐쇄 예정 블로그는 평소처럼 운영하므로 목록에 남긴다.
- **검색**: 검색어는 앞뒤 공백을 빼고 2~20자여야 하며, 한글·영문·숫자가 하나 이상 있어야 한다(6.1).
  - 이름·소개는 `MATCH(name, description) AGAINST(? IN BOOLEAN MODE)`(ngram 인덱스)로 찾는다. 이때 검색어는 따옴표로 묶어 구절 검색으로 만들어, 연산자 문자가 해석되지 않게 한다.
  - 태그는 검색어를 `TagNormalizer`로 바꾼 값과 같은 블로그 태그로 찾는다.
  - 두 결과를 합쳐(UNION) 목록과 같은 조건·정렬로 돌려준다.
  - 정렬 기본은 최신순이다. *가정*: 6.1의 검색 정렬 기본값이 따로 없어 목록과 같게 둔다.
- **이유**: FR-014, FR-015, D-88, D-89. 1차 데이터 규모에서는 MySQL 전문 검색으로 충분하다(헌장 VI).

## R-08 참여 신청

- **결정**: `JoinService.apply`는 신청자 회원 행을 잠그고 다음 순서로 확인한다. 회원 행을 잠그므로 같은 회원의 동시 신청이 대기 신청을 두 개 만들지 못한다.
  1. 메인 관리자면 거부한다.
  2. 열람할 수 없는 블로그면 404를 준다. 비공개 블로그도 신청을 받는지는 다음 단락의 가정을 본다.
  3. 이미 멤버·블로그장이면 거부한다.
  4. 블랙리스트에 걸리면 403 `BLOG_BLACKLISTED`를 주고 응답에 `appealAllowed`를 넣는다.
  5. 대기 중인 신청이 있으면 거부한다.
  6. 마지막 거절(REJECTED·AUTO_REJECTED)의 처리 시각이 7일 안이면 거부한다.
  7. 블로그장이 차단한 회원이면 `AUTO_REJECTED`로 저장하고 거절 알림을 보낸다. 응답은 일반 거절과 같은 `REJECTED`다.
  8. 자유 참여 블로그면 바로 멤버로 만들고, 승인제면 `PENDING`으로 둔다.
- **비공개 블로그 신청**: 비공개 블로그는 목록·검색에 없고 멤버만 볼 수 있어 신청 경로가 없다. *가정*: 비공개 블로그에는 신청을 받지 않는다(404). LINK 블로그는 링크로 들어온 사람이나 구독자가 신청할 수 있다.
- **멤버 수**: 멤버가 되거나 나갈 때 `blogs.member_count`를 같은 트랜잭션에서 고친다(D-89 인기순).
- **승인·거절**: 블로그 행을 잠그고 신청이 아직 `PENDING`인지 다시 확인한다. 두 관리자가 동시에 처리해도 한 번만 처리된다.

## R-09 블랙리스트 해시

- **결정**: 이름·이메일·전화번호를 각각 정규화한 뒤 HMAC-SHA256(비밀키 `BLACKLIST_HASH_SECRET`)으로 만든 16진수 64자를 저장한다.
  - 이메일은 소문자로 바꾼다.
  - 전화번호는 숫자만 남긴다.
  - 이름은 앞뒤 공백을 빼고 연속 공백을 하나로 줄인다.
- **이유**: 4.6은 "되돌릴 수 없는 값"을 요구한다. 전화번호는 경우의 수가 1억 개뿐이라 키 없는 SHA-256은 바로 거꾸로 계산된다. 비밀키를 쓰면 DB만 유출돼서는 원문을 찾을 수 없다.
- **주의**: 키를 바꾸면 기존 블랙리스트와 비교할 수 없게 되므로 키는 바꾸지 않는다. 키 교체가 필요해지면 별도 결정을 만든다.
- **검토한 다른 안**: bcrypt(같은 값을 비교하려면 행마다 비교해야 해 인덱스를 쓸 수 없음), 키 없는 SHA-256(전화번호를 쉽게 되돌림).

## R-10 제재와 정지 횟수

- **결정**: 경고·정지·해제·강퇴를 모두 `blog_sanctions`에 한 행씩 쌓는다.
  - 정지 기간은 `DAYS_3`, `DAYS_14`, `DAYS_30`, `PERMANENT`이고, `ends_at`은 시작 + 기간이며 영구 정지는 NULL이다.
  - 해제는 UNSUSPEND 행을 더하는 방식이고, 원래 정지 행은 고치지 않는다(기록 보존, FR-055).
  - 정지 횟수는 그 블로그에서 `starts_at`이 최근 1년 안인 SUSPEND 수다. 해제된 정지도 센다(D-95, D-98 #21). 3 이상이면 멤버 목록에 `kickSuggested = true`로 표시한다.
  - 대상이 부블로그장이면 블로그장만 처리할 수 있고, 블로그장은 대상이 될 수 없다.
- **강퇴 처리** (한 트랜잭션):
  1. KICK 기록을 남긴다.
  2. 멤버 행을 지우고 `member_count`를 1 줄인다.
  3. 그 블로그의 그 회원 글에 `author_left = true`를 표시한다.
  4. 블랙리스트 행을 추가한다.
  5. 끌 수 없는 알림을 보낸다.
- **1년 보관**: 제재·신고 기록 1년 삭제는 관리자 명세(005)의 보관 정리와 함께 만든다. 002는 기록만 쌓는다. *가정*

## R-11 블로그 안 신고 처리

- **결정**: 002는 `route = 'BLOG'`인 신고의 목록과 처리를 만든다. 신고를 만드는 기능(SOC-06)은 003에서 만들고, 002 테스트는 신고 행을 직접 넣는다.
  - 대상 회원은 target_type에 따라 정한다: USER는 target_id, POST는 posts.author_id, COMMENT는 comments.author_id다.
  - 처리 결과가 NONE이면 기록만 남기고, WARNING·SUSPEND·KICK이면 R-10과 같은 처리를 하고 `blog_sanctions.report_id`를 연결한다.
  - 처리하면 신고자에게 알림을 보낸다(설정 `report_result`).
- **접수처**: 블로그장에 대한 신고를 ADMIN으로 보내는 판단(D-93)은 신고를 만드는 003에서 한다. 002의 처리 API는 `route = 'BLOG'`만 다루므로 블로그장이 자기에 대한 신고를 볼 수 없다.

## R-12 위임과 블로그장 변경

- **결정**: 위임 요청은 블로그당 `PENDING` 하나만 둔다. 블로그 행을 잠근 뒤 확인한다. `expires_at`은 요청 + 7일(`blog.delegation.expire-after`)이다.
- **수락** (블로그 행 잠금, 한 트랜잭션):
  1. 이전 블로그장의 멤버 행을 `MEMBER`로 바꾸고 권한을 비운다.
  2. 받는 사람 행을 `OWNER`로 바꾸고 `manager_since`와 권한을 비운다.
  3. 요청을 `ACCEPTED`로 바꾼다.

  `owner_blog_id` 생성 컬럼이 유니크라, 이전 블로그장 행을 먼저 바꾸고 flush한 뒤 새 블로그장을 바꾼다.
- **자동 취소**: 04:00 처리에서 `status = 'PENDING' AND expires_at <= now`인 요청을 `AUTO_CANCELED`로 바꾸고 블로그장에게 알린다. 받는 사람이 응답할 때도 만료 여부를 다시 확인해, 04:00 전이라도 만료된 요청은 수락할 수 없다.
- **취소되는 경우**: 폐쇄 버튼을 누르면(FR-072) 대기 중인 요청을 `AUTO_CANCELED`로 바꾼다. 받는 사람이 그 사이 블로그를 나가거나 강퇴되어도 같은 처리를 한다. *가정*: 나가거나 강퇴된 사람은 받을 수 없으므로 함께 취소한다.
- **블로그장 강퇴 뒤 처리** (FR-082): `OwnerSuccessionService.revokeOwner(blogId)`를 만들고, 관리자 API(005)가 이를 부른다.
  - 부블로그장이 있으면 `manager_since`가 가장 이른 사람(같으면 id가 작은 사람)에게 넘긴다.
  - 없으면 `close_reason = 'OWNER_REVOKED'`로 폐쇄를 예약한다.
  - 박탈된 사람은 MEMBER로 남는다.
- **관리자 강제 폐쇄** (FR-084): `BlogClosingService.scheduleClose(blogId, ADMIN)`을 같은 방식으로 005에서 부른다.

## R-13 폐쇄 예약과 04:00 처리

- **폐쇄 예정 시각**: 누른 시각을 한국 시간 날짜로 바꾸고, 7일을 더한 날의 04:00이다(`blog.closing.grace-days=7`, `blog.closing.hour=4`).
- **알림 대상**: 블로그장을 뺀 멤버 전원과 구독자 전원을 합친 뒤 중복을 뺀다. 계산은 보낼 때마다 다시 한다. 3일 전에 새로 들어온 멤버도 받는다.
- **중복 방지**: 알림은 `blog_closing_notices`(블로그, 예정 시각, 시점, 회원 유니크)와 `notifications.event_key = BLOG_CLOSING:{blogId}:{예정시각}:{시점}`로 막는다. 둘 다 `INSERT IGNORE`로 넣어 다시 실행해도 한 번만 간다. 철회한 뒤 다시 폐쇄하면 예정 시각이 달라 새 회차가 된다.
- **04:00 처리 순서**: 001의 `DailyCleanupJob`(ShedLock `dailyCleanup`)에 블로그 단계를 더한다. 각 단계는 따로 트랜잭션을 써서 한 단계가 실패해도 다음 단계가 돈다.
  1. 만료된 위임 요청을 자동 취소한다.
  2. 폐쇄 예정 블로그 중 `close_scheduled_at - 3일 <= now`이고 D3를 아직 안 보낸 것에 D3 알림을 보낸다. D1도 같은 방식이다. 밀린 회차도 보낸다.
  3. `close_scheduled_at <= now`인 블로그를 폐쇄한다. 처리 내용:
     - `status = 'CLOSED'`, `closed_at = now`로 바꾼다.
     - 대기 중인 참여 신청과 해제 문의를 자동 거절하고 알린다(D-98 #15).
     - 대기 중인 위임 요청은 이미 폐쇄 버튼 때 취소됐다. 혹시 남아 있으면 다시 취소한다.
  4. `closed_at <= now - 30일`이고 주소가 아직 있는 블로그의 내용을 지운다. 처리 내용:
     - 글을 지운다. 좋아요·글 태그·조회 기록은 CASCADE로 함께 지워진다. 댓글은 `parent_id` 자기 참조 FK에 CASCADE가 없어, 대댓글 → 댓글 순서로 먼저 지운 뒤 글을 지운다.
     - 글 사진과 대표 이미지 파일·행, 카테고리, 해제 문의, 블랙리스트, 공유 링크, 블로그 태그를 지운다.
     - `address = NULL`로 바꾼다. 블로그 행, 멤버 행, 제재·신고 기록은 남긴다(D-86).
- **회원탈퇴와의 관계**: 001의 `OwnedBlogQuery`는 이미 `ACTIVE`·`CLOSING`만 세므로 폐쇄가 끝나면 탈퇴할 수 있다(FR-080).
- **이유**: FR-073~FR-081, D-12, D-13, D-14, D-86, SCL-03.

## R-14 알림 쓰기 (002 범위)

- **결정**: 002는 알림을 만들기만 한다. 알림 목록·읽음·30초 폴링 화면은 003(SOC-04)에서 만든다. `NotificationWriter.write(recipient, type, tab, target, actor, content, eventKey, settingKey)`를 만든다.
  - `INSERT IGNORE`로 넣어 `uk_notifications_recipient_id_event_key`가 중복을 막는다.
  - `settingKey`가 있으면 `notification_settings`를 확인한다. 행이 없으면 모두 켜진 것으로 본다.
  - `settingKey`가 null이면 끌 수 없는 알림이다.
  - 알림은 업무 트랜잭션 안에서 함께 넣는다. 처리가 롤백되면 알림도 남지 않는다.
- **알림 종류**: data-model의 "알림 종류" 표에 따른다.
- **FR-083** (블로그장의 참여 신청 알림 받기·보관 7일·일괄 삭제): 알림 설정 화면(SOC-04, 003)과 같은 화면이다. 002는 `notification_settings.join_request`를 존중해 쓰는 쪽만 만들고, 설정 화면은 003에서 만든다. *가정*

## R-17 동시성 잠금 정리

| 동작 | 잠그는 행 |
|---|---|
| 생성, 공개 범위 변경 | 블로그장 회원 행(users) |
| 참여 신청 | 신청자 회원 행 |
| 승인·거절, 제재, 강퇴, 부블로그장 지정·해제, 위임 요청·수락·거절, 폐쇄·철회, 블로그 탈퇴 | 블로그 행(blogs) |
| 04:00 처리 | ShedLock + 블로그마다 블로그 행 |

잠금 순서는 항상 users → blogs로 한다(교착 방지).

**구현에서 확인한 것 (2026-10-08)**: MySQL 기본 격리 수준(REPEATABLE READ)은 트랜잭션의 첫 일반 SELECT 때 스냅샷을 잡는다. 잠금(`SELECT ... FOR UPDATE`) 전에 다른 일반 읽기를 하면, 잠금을 기다린 뒤에도 그 뒤 일반 읽기는 예전 스냅샷을 본다(동시 생성 10번에 10개가 만들어진 원인). 그래서 잠그는 동작은 **잠금을 트랜잭션의 첫 읽기로** 둔다(`BlogLimitPolicy.lockUser`, `findByIdForUpdate`). 멤버 수는 엔티티 값이 아니라 `UPDATE blogs SET member_count = member_count + ?`로만 바꾼다.
